## 1. How experienced practitioners build a first eval set (error analysis, open/axial coding, starting size, growing from real failures)

### Takeaway
Before writing any metric, read real traces. Write free-text notes on the first thing that went wrong (open coding). Cluster the notes into 5–10 failure categories specific to the application (axial coding). Count them, fix the obvious ones, and build evaluators only for the failures that remain and matter. For a first eval suite, 20–50 tasks drawn from real failures is enough while the system is immature. Error analysis should aim for about 100 traces, or stop when no new failure types show up.

### Cited Findings
- **[Practitioner-primary]** The error-analysis loop has five steps: collect about 100 representative traces; read each one and mark it pass/fail with a note on what went wrong; group the failures into categories; label every trace against the categories; compute failure rates to set priorities. — [hamelsmu/evals-skills: error-analysis SKILL.md](https://github.com/hamelsmu/evals-skills/blob/main/skills/error-analysis/SKILL.md). → *Implication:* run the harness end to end on 20–30 real theses before designing any judge, and log full traces (collector queries, sources, advocate/skeptic/judge outputs).
- **[Practitioner-primary]** "~100 traces… is roughly where new traces stop revealing new kinds of failures". The stopping rule is "~100 traces reviewed with no new failure types appearing in the last 20". — [error-analysis SKILL.md](https://github.com/hamelsmu/evals-skills/blob/main/skills/error-analysis/SKILL.md); the FAQ describes the same idea as reaching "theoretical saturation… often dozens to ~100 to start" [snippet] — [Hamel's Evals FAQ](https://hamel.dev/blog/posts/evals-faq/). → *Implication:* for one person, stop annotating when 20 traces in a row add no new failure type. That may happen well before 100.
- **[Practitioner-primary]** Note "the **first thing that went wrong**" in each trace, because errors cascade. Write observations, not explanations ("SQL missed the budget constraint", not "the model probably didn't understand"). — [error-analysis SKILL.md](https://github.com/hamelsmu/evals-skills/blob/main/skills/error-analysis/SKILL.md). → *Implication:* in a multi-agent trace, record the most upstream failure (for example "collector only searched positive-framing queries") rather than the downstream verdict error it caused.
- **[Practitioner-primary]** Start grouping into categories after 30–50 traces. LLM-assisted clustering is fine after that point, but the human must review it, because "LLMs cluster by surface similarity". Aim for 5–10 categories that are distinct, clear enough for someone else to apply, and actionable. — [error-analysis SKILL.md](https://github.com/hamelsmu/evals-skills/blob/main/skills/error-analysis/SKILL.md); the FAQ says the same: "After you've open coded 30–50 traces yourself, use an LLM to organize your raw failure notes" and calls axial coding "the most important step" [snippet] — [Evals FAQ](https://hamel.dev/blog/posts/evals-faq/). → *Implication:* the harness's failure taxonomy should come from observation, not from the plan's list (dead theses, sycophancy and so on). Treat that list as hypotheses to confirm.
- **[Practitioner-primary]** Decision order for each category: (1) can it simply be fixed (missing prompt instruction, missing tool, engineering bug)? (2) is an evaluator worth building, given frequency, business impact and whether it will be used repeatedly? (3) if so, prefer code-based checks and use an LLM judge only when judgment is required. — [error-analysis SKILL.md](https://github.com/hamelsmu/evals-skills/blob/main/skills/error-analysis/SKILL.md). → *Implication:* on a one-person budget, many failures should become prompt or skill fixes rather than evals. Only recurring, high-impact failures deserve a standing evaluator.
- **[Practitioner-primary]** Newest version (Sept 2026): the first review sample is 15–25 items, about 60–70% cluster representatives and 30–40% random. "The goal is discovering failure modes, not estimating how common they are." The agent should wait until the human has annotated about 5 records before scanning the corpus for similar failures. — [ai-evals-course/evals-skills: error-discovery SKILL.md](https://github.com/ai-evals-course/evals-skills/blob/main/skills/error-discovery/SKILL.md) and [review-loop.md](https://github.com/ai-evals-course/evals-skills/blob/main/skills/error-discovery/review-loop.md). → *Implication:* a first review batch of about 20 harness runs, stratified by thesis type, is the current recommended starting point.
- **[Practitioner-primary]** When real data is sparse, generate synthetic inputs with dimension tuples. Start with 3 dimensions chosen where failures are expected, draft 20 tuples with the domain expert, and check that they are realistic. — [generate-synthetic-data SKILL.md](https://github.com/ai-evals-course/evals-skills/blob/main/skills/generate-synthetic-data/SKILL.md). → *Implication:* useful dimensions for the harness might be {thesis outcome: dead / winner / unresolved} × {user conviction: none / strong-pro / strong-con} × {market: B2B SaaS / consumer / regulated}.
- **[Vendor-eng]** "20-50 simple tasks drawn from real failures is a great start." Early agents show large effect sizes, so small samples are enough; mature agents need larger, harder evals. — [Anthropic, "Demystifying evals for AI agents" (Jan 9, 2026)](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents). → *Implication:* 20–50 cases in total across the five planned eval families is a legitimate v1.
- **[Vendor-eng]** Anthropic's Research feature started with about 20 queries representing real usage; prompt changes sometimes moved success from 30% to 80%, so small samples were enough to see the effects. — [Anthropic, "How we built our multi-agent research system" (Jun 13, 2025)](https://www.anthropic.com/engineering/multi-agent-research-system). → *Implication:* do not postpone evals until a large set exists. About 20 cases catches the big regressions in a research agent.
- **[Vendor-eng]** Sources of tasks: manual checks already done before release, common user tasks, bug trackers and support queues, prioritized by user impact. A good task is one where "two domain experts would independently reach the same pass/fail verdict". — [Demystifying evals](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents). → *Implication:* every harness failure seen in real use (a wrong kill, a missed kill, a fabricated citation) should go into the eval set. Discard cases whose correct verdict is genuinely ambiguous.
- **[Practitioner-primary]** Anti-patterns: brainstorming categories before reading traces; starting from a predefined list ("confirmation bias"); skipping the domain expert for the first 30–50 traces; treating error analysis as a one-off. Re-run it after new features, prompt rewrites, model switches and incidents. — [error-analysis SKILL.md](https://github.com/hamelsmu/evals-skills/blob/main/skills/error-analysis/SKILL.md). → *Implication:* re-run a short error-analysis pass whenever the skills (pesquisador-de-mercado, analista-imparcial) or the underlying model change.

### Inferences
- For a one-person harness, a realistic v1 is 20–30 fully read end-to-end runs, 5–10 named failure categories, and 20–50 frozen eval cases split between capability and regression. This matches both the Anthropic guidance and the Husain/Shankar guidance.
- The five planned eval families (dead theses, winners, sycophancy, collector neutrality, citation faithfulness) are reasonable hypotheses. The Husain/Shankar method says to check them against observed traces, which will probably surface failure modes not on the list (for example source-quality bias, stale data, or a misread TAM).

- I could not open the full Evals FAQ (hamel.dev was blocked), so I could not check its specific time-allocation claims (such as the share of development time spent on error analysis) or its guidance on agent "transition failure matrices". Both are left out.
- I found no source that gives a starting eval-set size specifically for judgment or forecasting agents, as distinct from task agents.

## 2. Validating LLM judges against human labels (Who Validates the Validators?, criteria drift, binary vs Likert, agreement metrics)

### Takeaway
LLM judges must be calibrated against a domain expert's binary labels with a train/dev/test split, reporting TPR and TNR rather than accuracy or kappa, and correcting aggregate rates for judge bias. Criteria cannot be fully specified before looking at outputs (criteria drift), so the rubric and the labels co-evolve and should be versioned. Binary pass/fail judges, each covering one failure mode, are the practitioner consensus. Anthropic's own research-agent judge used a single prompt with a 0–1 score plus pass/fail, which is a tension worth noting.

### Cited Findings
- **[Peer-reviewed]** "Criteria drift": "users need criteria to grade outputs, but grading outputs helps users define criteria". Some criteria depend on the specific outputs observed rather than being definable a priori, "raising serious questions for approaches that assume the independence of evaluation from observation of model outputs." EvalGen asks users to grade a subset of outputs and uses those grades to pick the candidate evaluators (Python assertions or LLM-grader prompts) that best match. The qualitative study found support but "underscores the subjectivity and iterative process of alignment." [snippet] — [Shankar, Zamfirescu-Pereira, Hartmann, Parameswaran, Arawjo, "Who Validates the Validators?" (UIST 2024)](https://arxiv.org/abs/2404.12272); venue: [ACM DL](https://dl.acm.org/doi/abs/10.1145/3654777.3676450). → *Implication:* write the harness's pass/fail definitions (for example what counts as a "fair kill") only after grading real outputs, version the rubric, and expect to relabel earlier cases when it changes.
- **[Practitioner-primary]** Judge validation protocol: split about 100 human-labeled traces into train 10–20% (source of few-shot examples), dev 40–45% (iterate) and test 40–45% (run once). Aim for about 50 Pass / 50 Fail, balanced even if the real distribution is skewed. Labels should come from a domain expert, not outsourced annotators. Target TPR and TNR > 90% on dev; the minimum acceptable is > 80%. — [hamelsmu/evals-skills: validate-evaluator SKILL.md](https://github.com/hamelsmu/evals-skills/blob/main/skills/validate-evaluator/SKILL.md) (unchanged in the [Sept 2026 successor repo](https://github.com/ai-evals-course/evals-skills)). → *Implication:* the one person running the harness is the principal domain expert. About 100 binary labels per judge is a real but finite cost, so validate only the 1–3 judges that matter most (for example citation-support and fair-kill).
- **[Practitioner-primary]** Use TPR/TNR, not precision/recall or raw accuracy. "Use Cohen's Kappa only for measuring agreement between two human annotators, not for judge-vs-ground-truth." Under class imbalance, a judge that always says Pass gets 90% accuracy while catching zero failures. — [validate-evaluator SKILL.md](https://github.com/hamelsmu/evals-skills/blob/main/skills/validate-evaluator/SKILL.md); [eval-audit SKILL.md](https://github.com/hamelsmu/evals-skills/blob/main/skills/eval-audit/SKILL.md). → *Implication:* report the judge's TNR on "should kill" cases and its TPR on "should survive" cases separately. Kappa only applies if a second person ever labels.
- **[Practitioner-primary]** Aggregate pass rates from an imperfect judge should be corrected with the Rogan-Gladen formula θ̂ = (p_obs + TNR − 1)/(TPR + TNR − 1), with a bootstrap 95% CI. The `judgy` package implements this. Worked example: raw 80% becomes a corrected 85% when TPR = 0.92 and TNR = 0.88. "Below 60 [labels], confidence intervals become wide." Improving TPR narrows the CI more than improving TNR does. — [validate-evaluator SKILL.md](https://github.com/hamelsmu/evals-skills/blob/main/skills/validate-evaluator/SKILL.md). → *Implication:* with 20–50 eval cases, always report CIs. A change from 70% to 80% on 20 cases is noise unless the CI says otherwise.
- **[Practitioner-primary]** Binary pass/fail only, with no Likert scales: "annotators disagree on the difference between a 3 and a 4, and the judge inherits that noise." Capture severity with several binary judges (for example "factually wrong" and "dangerously wrong"). One judge covers one failure mode. The prompt has four parts: criterion, pass/fail definitions, 2–4 few-shot examples (including a borderline case) drawn only from the train split, and structured output with the critique before the verdict. — [write-judge-prompt SKILL.md](https://github.com/hamelsmu/evals-skills/blob/main/skills/write-judge-prompt/SKILL.md). → *Implication:* do not build a "rate the analysis 1–5" judge. Use separate binary checks such as "verdict cites at least one disconfirming source", "probability consistent with stated evidence" and "no unsupported claims".
- **[Practitioner-primary]** "Critique shadowing": one principal domain expert ("one is better than many") answers the yes/no question "Did the AI achieve the desired outcome?" and writes a critique detailed enough to serve as a few-shot example for the judge. — [Hamel Husain, "Creating a LLM-as-a-Judge That Drives Business Results"](https://hamel.dev/blog/posts/llm-judge/) [snippet]; summarized by [Simon Willison (Oct 30, 2024)](https://simonwillison.net/2024/Oct/30/llm-as-a-judge/) [Aggregator]. → *Implication:* keep a spreadsheet of pass/fail plus a critique for each harness verdict. The critiques become the judge's few-shot examples.
- **[Practitioner-primary]** Operational hygiene: pin exact judge model versions ("Providers update models without notice, causing silent drift"). Re-validate after changing the judge prompt or model. Never use dev/test items as few-shot examples (leakage). Do not report dev-set numbers as final. — [validate-evaluator SKILL.md](https://github.com/hamelsmu/evals-skills/blob/main/skills/validate-evaluator/SKILL.md). → *Implication:* record the judge model ID in each eval run's metadata, and keep the few-shot cases out of the scored set.
- **[Vendor-eng]** Model-based graders are "non-deterministic, more expensive than code, requires calibration with human graders". Give the judge an "out" (return "Unknown" when uncertain). Grade each dimension with an isolated LLM judge rather than all at once. "LLM-based rubrics should be frequently calibrated against expert human judgment." — [Demystifying evals](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents). → *Implication:* add an "insufficient evidence" option to the citation-support judge so that "can't verify" is not forced into "supported".
- **[Vendor-eng]**, which is in tension with the practitioner guidance above: for the Research feature, "a single LLM call with a single prompt outputting scores from 0.0-1.0 and a pass-fail grade was the most consistent and aligned with human judgements". Its rubric covered factual accuracy, citation accuracy, completeness, source quality and tool efficiency. — [Multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system). This conflicts with the "one judge per dimension, binary only" advice from [write-judge-prompt SKILL.md](https://github.com/hamelsmu/evals-skills/blob/main/skills/write-judge-prompt/SKILL.md) and with Anthropic's own later guidance to use isolated per-dimension judges ([Demystifying evals, Jan 2026](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)). → *Implication:* a single combined judge is a cheap first pass. Split it into per-criterion binary judges once you need to know *which* criterion failed. The newer Anthropic post leans toward splitting.

### Inferences
- The harness itself uses an LLM "blind judge". Its verdicts are the system's output, not the eval grader, but the same validation logic applies: the blind judge's kill/keep decision on known-outcome cases is a binary classifier and should be scored with TPR/TNR plus CIs.
- Criteria drift implies the eval rubric for "good business-thesis judgment" will change as the user reads outputs. Keep a dated rubric changelog in the repo alongside the eval cases.

### Gaps
- Could not open the Shankar et al. paper's full text (arXiv, ACM and Berkeley were blocked), so specific quantitative results (number of participants, alignment numbers) are not reported.
- I found no source that directly tests judge alignment for *probabilistic* verdicts (as opposed to pass/fail) against humans.

## 3. Agent-specific evals (end-state vs trajectory grading, pass@k vs pass^k, variance, grader types, Anthropic guidance)

### Takeaway
Grade outcomes and final artifacts first ("what the agent produced, not the path it took"). Add a few targeted transcript checks. Mix code, model and human graders. Run several trials per task and report pass^k when consistency matters, which it does for a verdict engine. Isolate trials, read transcripts, and split capability evals (low pass rate) from regression evals (near 100%).

### Cited Findings
- **[Vendor-eng]** Definitions: *task* (inputs plus success criteria); *trial* (one attempt, run several because outputs vary); *grader*; *transcript* (the full record of outputs, tool calls and reasoning); *outcome* (final environment state, distinct from what the agent *says*: "a flight-booking agent might say 'Your flight has been booked' but the outcome is whether a reservation exists"). — [Demystifying evals (Grace, Hadfield, Olivares, De Jonghe; Jan 9, 2026)](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents). → *Implication:* the harness's "outcome" is its saved artifacts (evidence file, verdict JSON with probability, buyer-test plan). Grade those files, not the chat summary.
- **[Vendor-eng]** Grader types. Code-based: "fast, cheap, objective, reproducible" but brittle. Model-based: flexible but non-deterministic and needs calibration. Human: gold standard but slow and expensive, and used to calibrate model graders. Scores can be weighted, binary (all must pass) or hybrid. — [Demystifying evals](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents). → *Implication:* push as much as possible into code checks (every citation URL resolves, quoted text appears in the fetched source, probability is between 0 and 1, the verdict file has the required fields, the blind judge's input contains no user-conviction text).
- **[Vendor-eng]** "It's often better to grade what the agent produced, not the path it took", to avoid penalizing valid alternative approaches. Build in partial credit. — [Demystifying evals](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents). The multi-agent post also recommends "end-state evaluation rather than turn-by-turn analysis" for agents that change state over many turns. — [Multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system). → *Implication:* score the final verdict and evidence set, not the order of searches. Use trajectory checks only for invariants such as isolation between advocate, skeptic and judge.
- **[Vendor-eng]** pass@k is the probability of at least one success in k trials, and it rises with k. pass^k is the probability that *all* k trials succeed, and it falls with k: 75% per trial over 3 trials gives (0.75)³ ≈ 42%. "pass@k for tools where one success matters, pass^k for agents where consistency is essential." — [Demystifying evals](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents). → *Implication:* a verdict engine needs consistency. Run each known-outcome case 3 times and report pass^3 (for example "killed the dead thesis in all 3 runs") together with the spread of the probability estimates.
- **[Vendor-eng]** "Each trial should be 'isolated' by starting from a clean environment. Unnecessary shared state between runs (leftover files, cached data, resource exhaustion) can cause correlated failures." — [Demystifying evals](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents). → *Implication:* clear harness memory, notes folders and cached evidence between eval trials so that earlier verdicts on the same company cannot leak in.
- **[Vendor-eng]** Capability ("quality") evals should start at a low pass rate. Regression evals should sit near 100%. Capability tasks "graduate" to regression once they pass reliably. Watch for saturation, meaning all solvable tasks pass. "With frontier models, a 0% pass rate across many trials is most often a signal of a broken task, not an incapable agent." — [Demystifying evals](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents). → *Implication:* keep two lists, "hard cases we still fail" and "cases we must never regress on". If a case always fails, check its reference answer before blaming the harness.
- **[Vendor-eng]** Balanced problem sets: "Test both cases where a behavior should occur and where it shouldn't. One-sided evals create one-sided optimization." — [Demystifying evals](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents). → *Implication:* the dead-thesis set (should kill) and the winner set (should not kill) must be roughly the same size. A cheap-kill tuned only on dead theses will learn to kill everything.
- **[Vendor-eng]** Research agents: ground truth shifts and outputs are long and open-ended. Combine groundedness checks (claims supported by sources), coverage checks (key facts included) and source-quality checks (authoritative sources). — [Demystifying evals](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents). → *Implication:* these map directly to the planned citation-faithfulness eval and to a collector-coverage eval ("did it find the known key fact, e.g. the regulatory ban that killed company X?").
- **[Vendor-eng]** Human testers of the research system found that "early agents consistently chose SEO-optimized content farms over authoritative but less highly-ranked sources like academic PDFs or personal blogs". Multi-agent systems "have emergent behaviors" that automation misses. — [Multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system). → *Implication:* add a source-quality check for the collector (share of primary sources such as filings, pricing pages and regulator documents versus listicles or SEO blogs), and keep periodic manual trace reading.
- **[Vendor-eng]** "You won't know if your graders are working well unless you read the transcripts… Failures should seem fair." Evals are "a living artifact that needs ongoing attention and clear ownership". Automated evals, production monitoring, user feedback, manual transcript review and human studies are complementary layers. — [Demystifying evals](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents). → *Implication:* budget a fixed small slot, such as reading 5 transcripts after each eval run, instead of trusting the aggregate score.
- **[Vendor-eng]** Anthropic found infrastructure bugs that distorted scores: Opus 4.5 on CORE-Bench "initially scored 42%" and reached 95% after bugs in the eval were fixed. — [Demystifying evals](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents). → *Implication:* when the harness scores badly, check the eval case and grader before changing the harness.

### Inferences
- A harness with separate advocate, skeptic and blind-judge roles needs at least one *trajectory* invariant check even though end-state grading is preferred: the blind judge's input must not contain the user's conviction or the advocate's identity. That is a cheap code check on the logged prompt.
- Probability outputs vary between runs as well as verdicts. Reporting the standard deviation of P(success) across 3 trials is a cheap stability metric that complements pass^3.

### Gaps
- I did not find published numbers on typical run-to-run variance of LLM probability estimates for business or forecasting judgments.
- OpenAI's agent-eval guidance (platform.openai.com) was blocked and could not be reviewed.

## 4. Evaluating judgment/research systems whose outcomes are delayed or unknown (backtesting, resolved predictions, counterfactual consistency)

### Takeaway
Three complementary strategies apply. (a) Backtest on historical cases with known outcomes, being careful about temporal and "logical" leakage and about the model memorizing famous outcomes. (b) Score prospective predictions with proper scoring rules (Brier or log score) as they resolve, which is the ForecastBench approach. (c) Run consistency and counterfactual checks that need no ground truth at all: negation and paraphrase coherence, and the same input with and without user conviction. For sycophancy, the key design is a neutral/agree/disagree persona set measuring verdict drift.

### Cited Findings
- **[Peer-reviewed]** Backtested LLM-forecaster evals suffer from (1) many forms of *temporal leakage* and (2) poor extrapolation from benchmark to real-world forecasting. *Logical leakage* example: "Will Queen Elizabeth live to be 100?" can be answered "No" by a model that knows it is being evaluated after her death. *Back-generated questions* (built from news after the fact) are biased because "news is biased towards events that occur and rarely reports uninteresting events that unsurprisingly did not occur." [snippet] — [Paleka, Goel, Geiping, Tramèr, "Pitfalls in Evaluating Language Model Forecasters"](https://arxiv.org/abs/2506.00723) (ICLR 2026 per [ML Anthology](https://mlanthology.org/iclr/2026/paleka2026iclr-pitfalls/)). → *Implication:* famous dead or winning companies (Theranos, Quibi, Airbnb) are contaminated because the model and web search both "know" the outcome. The backtest mostly measures recall. Prefer obscure cases, anonymize or disguise names, and restrict evidence to material dated before the decision point.
- **[Preprint, titles only]** Recent work specifically measures leakage in date-filtered search and in LLM backtesting: "Temporal Leakage in Search-Engine Date-Filtered Web Retrieval: A Retrospective Forecasting Case Study" ([arXiv 2602.00758](https://arxiv.org/pdf/2602.00758)) and "Temporal Leakage in LLM Backtesting: Measurement, Validation, and Adjusted Scores" ([arXiv 2608.02985](https://arxiv.org/pdf/2608.02985)). I saw only the titles in search results; the contents were not verified. → *Implication:* do not trust the collector's live web search to respect a "pretend it's 2019" instruction. Date filters leak. For backtests, give a frozen, pre-dated evidence pack instead of live search.
- **[Peer-reviewed]** Consistency checks allow instant, ground-truth-free evaluation of forecasters. An arbitrage-based metric measures how much an arbitrageur could profit from incoherent forecasts (for example P(Dem wins) = 60% and P(Rep wins) = 60%). A frequentist, hypothesis-test metric is also defined. Ten rules are covered: Negation, Paraphrase, Consequence, AndOr, And, Or, But, Cond, CondCond, ExpEvidence. It was an ICLR 2025 oral. [snippet] — [Paleka et al., "Consistency Checks for Language Model Forecasters"](https://arxiv.org/abs/2412.18544); [ICLR 2025 oral page](https://iclr.cc/virtual/2025/oral/31766). Code and datasets are public at [github.com/dpaleka/consistency-forecasting](https://github.com/dpaleka/consistency-forecasting) (datasets on Hugging Face as `dpaleka/ccflmf`). → *Implication:* cheap evals for calibrated probabilities: ask the harness for P(thesis) and P(not thesis) in separate runs (Negation), rephrase the thesis (Paraphrase), and check P(narrower claim) ≤ P(broader claim) (Consequence). Incoherence is a failure that needs no ground truth.
- **[Peer-reviewed/benchmark]** ForecastBench avoids leakage by scoring only questions that were *unresolved at submission time*. It uses Brier and log scores and compares against human forecasters and superforecasters. It found LLMs underperform superforecasters. [snippet] — [ForecastBench](https://www.forecastbench.org/); [paper](https://arxiv.org/html/2409.19839v5). → *Implication:* log every live harness verdict with a probability, a resolution criterion and a resolution date. Score the log with the Brier score as outcomes arrive (for example "buyer test gets ≥ N pre-orders by date D"). This is the only fully leakage-free evaluation.
- **[Aggregator/Preprint, snippet]** For sycophancy, a three-persona design (neutral, agree, disagree) "separates… persona independent opinion bias (same verdict across all personas) and sycophantic drift (verdict tracks the user's persona)". — search summary attributed to [arXiv 2604.21564, "Measuring Opinion Bias and Sycophancy via LLM-based Persuasion"](https://arxiv.org/pdf/2604.21564). A paired-prompt pattern (neutral vs leading-premise version of each item) is described by a vendor glossary ([FutureAGI](https://futureagi.com/glossary/sycophancy-in-llm/)). A "turn of flip" metric (how quickly a model gives in to pushback over multiple turns) appears in [Findings of EMNLP 2025](https://aclanthology.org/2025.findings-emnlp.121.pdf). → *Implication:* the planned "with vs without user conviction" test should have three arms (no conviction / "I'm convinced this works" / "I'm convinced this fails"). Report the probability shift Δ between arms. A neutral system has Δ ≈ 0, and a shared offset across all three arms indicates bias rather than sycophancy.
- **[Vendor-eng, snippet]** OpenAI's GPT-4o sycophancy incident (April 2025): "offline evaluations—especially those testing behavior—generally looked good, and the A/B tests seemed to indicate that the small number of users who tried the model liked it". Expert testers raised subjective concerns about the model's "feel", but these did not block launch. OpenAI said it would treat behavior issues as launch-blocking. — [OpenAI, "Expanding on what we missed with sycophancy"](https://openai.com/index/expanding-on-sycophancy/); summary by [Simon Willison (May 2, 2025)](https://simonwillison.net/2025/May/2/what-we-missed-with-sycophancy/) [Aggregator]. → *Implication:* make the sycophancy eval a blocking regression gate for any skill or prompt change, and give weight to the owner's qualitative sense that "it's agreeing with me too much".
- **[Practitioner-primary]** In grounded generation, faithfulness failures are hallucinations ("even correct facts from the LLM's own knowledge count as hallucinations"), omissions (relevant context ignored) and misinterpretations. Evaluate retrieval and generation separately, and do not use ROUGE, BERTScore or cosine similarity as the primary generation metric. — [ai-evals-course/evals-skills: evaluate-rag SKILL.md](https://github.com/ai-evals-course/evals-skills/blob/main/skills/evaluate-rag/SKILL.md). → *Implication:* for citation faithfulness, (1) use code to check that each cited URL was actually fetched by the collector and that any quoted span appears verbatim, then (2) use a binary LLM judge per claim–source pair (supported / not supported / can't tell). Treat correct-but-uncited facts from model memory as failures, because the collector is supposed to be evidence-only.
- **[Vendor-eng]** Anthropic's research-agent rubric includes "Factual accuracy: Do claims match sources?" and "Citation accuracy: Do cited sources match the claims?" as separate criteria. — [Multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system). → *Implication:* split citation faithfulness into two checks: claim → source ("is this claim backed?") and source → claim ("does this source actually say that?").

### Inferences
- Collector neutrality can be tested counterfactually in the same way as sycophancy. Give the collector the same thesis framed positively ("prove X works") and negatively ("prove X fails"), or with and without the user's conviction, then compare the evidence sets: overlap of sources, and the ratio of supporting to disconfirming items. A neutral collector should return similar sets. This extends the three-persona sycophancy design to the collection stage (my own extension, not taken from a source).
- A cheap memorization probe for backtest cases: before using a "known dead" or "known winner" case, ask the model directly "what happened to company X?". If it knows, either anonymize the case or label it "contaminated". Contaminated cases can still serve as regression tests, but they do not measure judgment.
- Survivorship caution for the dead/winner sets, based on the Pitfalls paper's point about news bias: sets built from famous failures and famous successes over-represent dramatic outcomes. Also include "boring" middle cases (companies that neither died nor broke out), or the eval rewards extreme verdicts.
- For a one-person budget, the ranking by value per unit of cost is probably: (1) code checks on citations and verdict schema; (2) three-arm sycophancy pairs on about 10 theses × 3 trials; (3) balanced known-outcome backtests (about 10 dead, about 10 winners, a few in the middle) using frozen evidence packs; (4) negation and paraphrase consistency checks; (5) a Brier-scored forward log that grows over months.

The web-search budget ran out before I could check finance "look-ahead bias" work on anonymizing company names in LLM backtests. It is worth a follow-up search.

## 5. Common eval anti-patterns (generic metrics, off-the-shelf scores, too many criteria)

### Takeaway
The recurring failures are: measuring generic qualities (helpfulness, hallucination score, coherence, ROUGE or BERTScore) instead of observed failure modes; holistic or Likert judges; judges that were never validated or were scored by raw accuracy; leakage between few-shot and test data; one-sided eval sets; building evaluators before fixing obvious prompt bugs; and treating evals as one-off. For a one-person harness, too many criteria is a real risk. Aim for 5–10 failure categories, and standing evaluators only for the few that recur and matter.

### Cited Findings
- **[Practitioner-primary]** Generic labels borrowed from research ("hallucination score", "toxicity", "coherence") suggest the categories were brainstormed rather than observed. Such evaluators "score well on paper but miss real problems". — [eval-audit SKILL.md](https://github.com/hamelsmu/evals-skills/blob/main/skills/eval-audit/SKILL.md). → *Implication:* do not adopt an off-the-shelf "faithfulness score" or "helpfulness score". Name harness-specific failures (for example "killed on a single outdated source", "probability moved with user conviction").
- **[Practitioner-primary]** "ROUGE, BERTScore, cosine similarity, or embedding distance used as the main evaluator for generation quality" measure surface overlap, not correctness. — [eval-audit SKILL.md](https://github.com/hamelsmu/evals-skills/blob/main/skills/eval-audit/SKILL.md). → *Implication:* never compare harness verdict prose to a reference memo by similarity. Grade the discrete verdict, the probability and specific claims.
- **[Practitioner-primary]** Holistic judges ("Is this response helpful?", "Rate the quality") "produce unactionable verdicts". Use one failure mode per judge, and use code instead of LLM judges for anything objectively checkable (format, constraints, keywords, schema). — [eval-audit SKILL.md](https://github.com/hamelsmu/evals-skills/blob/main/skills/eval-audit/SKILL.md); [write-judge-prompt SKILL.md](https://github.com/hamelsmu/evals-skills/blob/main/skills/write-judge-prompt/SKILL.md). → *Implication:* before writing an LLM judge, ask whether a regex or script can check it. Many harness checks can be scripts (URL present, date of source before cutoff, probability field present, advocate and skeptic both cited ≥ 1 source).
- **[Practitioner-primary]** "Building evaluators before fixing obvious problems": fix prompt gaps, missing tools and bugs first. Reserve evaluators for failures "the user will iterate on repeatedly". "Will this evaluator actually get used… or is it checkbox work?" — [error-analysis SKILL.md](https://github.com/hamelsmu/evals-skills/blob/main/skills/error-analysis/SKILL.md). → *Implication:* cap the harness at a handful of standing evaluators. The five planned families are already near the ceiling for one person.
- **[Practitioner-primary]** Review-process anti-patterns: reviewers see only final outputs rather than full traces ("hides where the pipeline broke"); traces shown as raw JSON; outsourced annotators without domain expertise; evaluators never re-validated as the pipeline changes. — [eval-audit SKILL.md](https://github.com/hamelsmu/evals-skills/blob/main/skills/eval-audit/SKILL.md). → *Implication:* a small script that renders each harness run (evidence → advocate → skeptic → judge) as readable markdown or HTML is probably the highest-return eval tool to build.
- **[Practitioner-primary]** Judge-validation anti-patterns: assuming judges "just work"; raw accuracy or percent agreement; dev/test examples used as few-shot; reporting dev performance as final; raw judge rates without bias correction; point estimates without CIs. — [validate-evaluator SKILL.md](https://github.com/hamelsmu/evals-skills/blob/main/skills/validate-evaluator/SKILL.md). → *Implication:* with small n, report "7/10 dead theses killed in all 3 runs (pass^3), 95% CI [..]" rather than a bare percentage.
- **[Vendor-eng]** One-sided evals "create one-sided optimization". Shared state between trials causes correlated failures. Graders must not be gameable ("passing requires genuinely solving the problem"). A 0% pass rate usually means a broken task. — [Demystifying evals](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents). → *Implication:* balance kill and survive cases, isolate runs, and make sure the harness cannot pass the "winner" cases by always hedging at 50%. Score probabilities with the Brier score so that hedging is penalized.
- **[Vendor-eng, snippet]** Offline behavior evals and small A/B tests can look good while missing a behavioral problem such as sycophancy. Qualitative expert concerns should carry blocking weight. — [OpenAI, "Expanding on what we missed with sycophancy"](https://openai.com/index/expanding-on-sycophancy/). → *Implication:* aggregate scores alone are insufficient. Keep manual transcript reading as a gate.
- **[Practitioner-primary]** Synthetic data anti-pattern: overfitting to synthetic eval data; "Validate against real user queries regularly." Generating synthetic data is not recommended if 100+ real representative traces already exist. — [evaluate-rag SKILL.md](https://github.com/ai-evals-course/evals-skills/blob/main/skills/evaluate-rag/SKILL.md); [generate-synthetic-data SKILL.md](https://github.com/ai-evals-course/evals-skills/blob/main/skills/generate-synthetic-data/SKILL.md). → *Implication:* use synthetic theses only to fill gaps (for example rare sectors). Replace them with real theses the user actually brought as usage grows.

### Inferences
- "Too many criteria" is mostly addressed by the decision rule "fix first, evaluator only if recurring and high-impact", plus the 5–10 category cap. Neither source gives a hard maximum number of judges.
- Anthropic's single-prompt five-criterion rubric (0–1 plus pass/fail) is a defensible low-cost starting point for a one-person harness, provided a human reads the flagged cases. The Husain/Shankar approach (one binary judge per failure mode) is more diagnostic but costs more labels.

### Gaps
- I found no source that quantifies how many evaluators one person can realistically maintain.
- OpenAI's "evaluation best practices" guide (which reportedly lists anti-patterns such as generic metrics and vibe-based evals) could not be fetched, so it is not cited.
