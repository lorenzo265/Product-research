## 1. "Building effective agents": workflows vs agents, the five patterns, when to add complexity

### Takeaway
Anthropic separates **workflows** (LLMs and tools orchestrated through predefined code paths) from **agents** (LLMs that direct their own process and tool use). It names five workflow patterns plus the autonomous agent, and says to add complexity only when it "demonstrably improves outcomes." The post now carries a banner saying its tooling landscape is out of date and pointing to Managed Agents. The design principles still hold and are cited by 2026 posts.

### Cited Findings
- [Eng. post] Definitions: "Workflows are systems where LLMs and tools are orchestrated through predefined code paths. Agents, on the other hand, are systems where LLMs dynamically direct their own processes and tool usage." — [Building effective agents](https://www.anthropic.com/research/building-effective-agents). → Harness: the fixed evidence → advocate/skeptic → judge pipeline is a *workflow*. Only the open-ended discovery and research steps need to be *agents*.
- [Eng. post] **Superseded banner (flag):** "Much of the tooling landscape described in this post has changed since December 2024. For our current approach, see how we built Claude Managed Agents." The framework list now reads: Claude Agent SDK, Strands Agents SDK (AWS), Rivet, Vellum. The routing example now names Claude Haiku 4.5 and Sonnet 4.5. — [Building effective agents](https://www.anthropic.com/research/building-effective-agents). → Harness: use the post for principles, and use 2026 posts and docs for mechanics.
- [Eng. post] When to add complexity: "find the simplest solution possible, and only increasing complexity when needed. This might mean not building agentic systems at all… For many applications, however, optimizing single LLM calls with retrieval and in-context examples is usually enough." Also: "you should consider adding complexity only when it demonstrably improves outcomes." — [Building effective agents](https://www.anthropic.com/research/building-effective-agents). → Harness: each subagent or stage should earn its place against an eval, for example a single-call judge vs the advocate/skeptic/judge trio.
- [Eng. post] Building block, the **augmented LLM** (retrieval, tools, memory). Focus on "tailoring these capabilities to your specific use case and ensuring they provide an easy, well-documented interface for your LLM." — [same](https://www.anthropic.com/research/building-effective-agents).
- [Eng. post] **Prompt chaining**: a sequence of calls with programmatic "gates" between steps. Use it "where the task can be easily and cleanly decomposed into fixed subtasks… trade off latency for higher accuracy." — [same](https://www.anthropic.com/research/building-effective-agents). → Harness: put deterministic Python gates between stages, e.g. reject an evidence record with no source URL before it reaches judgment.
- [Eng. post] **Routing**: classify the input and send it to a specialized follow-up. Useful where "distinct categories… are better handled separately." One example sends easy queries to Haiku 4.5 and hard ones to Sonnet 4.5. — [same](https://www.anthropic.com/research/building-effective-agents). → Harness: route opportunity types (B2B SaaS, marketplace, services arbitrage, regulated niche) to specialized research prompts, and route cheap screening to smaller models.
- [Eng. post] **Parallelization**, in two forms. *Sectioning* splits work into independent subtasks. *Voting* runs the same task several times, e.g. "multiple prompts evaluating different aspects or requiring different vote thresholds to balance false positives and negatives." For guardrails, a separate screening call "tends to perform better than having the same LLM call handle both." — [same](https://www.anthropic.com/research/building-effective-agents). → Harness: the judge could be a vote across independent judges with an explicit threshold. The guardrail advice supports keeping evidence screening apart from judgment.
- [Eng. post] **Orchestrator-workers**: a central LLM breaks the task down dynamically, delegates, and synthesizes. Fits "complex tasks where you can't predict the subtasks needed." Example: "Search tasks that involve gathering and analyzing information from multiple sources." — [same](https://www.anthropic.com/research/building-effective-agents). → Harness: this is the evidence-collection phase.
- [Eng. post] **Evaluator-optimizer**: one call generates and another evaluates in a loop. It fits when "we have clear evaluation criteria, and when iterative refinement provides measurable value." Example: "Complex search tasks… where the evaluator decides whether further searches are warranted." — [same](https://www.anthropic.com/research/building-effective-agents). → Harness: the skeptic or judge can send an "insufficient evidence, search X" signal back to the collectors.
- [Eng. post] **Agents**: "typically just LLMs using tools based on environmental feedback in a loop." They need "ground truth from the environment at each step," may pause for human feedback at checkpoints, and should have stopping conditions such as max iterations. "The autonomous nature of agents means higher costs, and the potential for compounding errors." — [same](https://www.anthropic.com/research/building-effective-agents). → Harness: real-buyer validation (interviews, pre-sales) is the ground truth. Put human checkpoints before outreach or spend.
- [Eng. post] Three principles: "Maintain simplicity in your agent's design. Prioritize transparency by explicitly showing the agent's planning steps. Carefully craft your agent-computer interface (ACI) through thorough tool documentation and testing." — [same](https://www.anthropic.com/research/building-effective-agents).
- [Eng. post] Appendix 1: agents add most value where tasks have "both conversation and action… clear success criteria, enable feedback loops, and integrate meaningful human oversight." — [same](https://www.anthropic.com/research/building-effective-agents).
- [Eng. post] Appendix 2 (tools/ACI): "we actually spent more time optimizing our tools than the overall prompt." Requiring absolute file paths removed relative-path errors ("the model used this method flawlessly"). "Poka-yoke your tools." — [same](https://www.anthropic.com/research/building-effective-agents). → Harness: Python helper scripts should take absolute paths and validate arguments.

### Inferences
- The harness is a hybrid. Research and discovery are orchestrator-workers (agentic). Adjudication is parallelization/voting plus evaluator-optimizer (workflow). Both halves map onto named patterns, so the design is conventional rather than exotic.
- "Add complexity only when it demonstrably improves outcomes" means the advocate/skeptic/judge trio needs an ablation against simpler baselines: one judge with a rubric, or a judge plus a skeptic only.

### Gaps
- The post gives no quantitative thresholds for "when to go agentic." It is qualitative guidance.
- The current Managed Agents docs referenced by the banner were not fully read. Only the engineering post on Managed Agents was (see §5).

## 2. "How we built our multi-agent research system": architecture, effort scaling, variance drivers, failure modes, evaluation, cost

### Takeaway
An Opus 4 lead with Sonnet 4 subagents beat single-agent Opus 4 by **90.2%** on Anthropic's internal research eval. Token usage alone explained **80%** of variance on BrowseComp, and tokens, tool calls and model together explained **95%**. Multi-agent runs use about **15×** the tokens of chat. Effort-scaling rules and detailed delegation specs in the prompts were the main levers. Evaluation started with about 20 real queries, a single rubric LLM judge (0.0–1.0 scores plus pass/fail) and human testing.

### Cited Findings
- [Eng. post] Architecture: orchestrator-worker. A LeadResearcher plans, "saving its plan to Memory to persist the context, since if the context window exceeds 200,000 tokens it will be truncated". It then spawns parallel subagents that search with interleaved thinking, synthesizes, decides whether more research is needed, and finally hands off to a **CitationAgent** that attributes claims to sources. — [Multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system). → Harness: persist the research plan to a file first, and keep a separate citation/attribution pass. This matches the harness's evidence-ledger separation.
- [Eng. post] Performance: "a multi-agent system with Claude Opus 4 as the lead agent and Claude Sonnet 4 subagents outperformed single-agent Claude Opus 4 by 90.2% on our internal research eval." It excels at "breadth-first queries that involve pursuing multiple independent directions simultaneously." — [same](https://www.anthropic.com/engineering/multi-agent-research-system). → Harness: market scans (many niches, cities, competitors) are breadth-first and suit fan-out. Deep validation of one thesis suits it less.
- [Eng. post] Variance drivers: "three factors explained 95% of the performance variance in the BrowseComp evaluation… token usage by itself explains 80% of the variance, with the number of tool calls and the model choice as the two other explanatory factors." Also: "upgrading to Claude Sonnet 4 is a larger performance gain than doubling the token budget on Claude Sonnet 3.7." — [same](https://www.anthropic.com/engineering/multi-agent-research-system). → Harness: collection quality is mostly a token and tool-call budget question. Pick the best model for collectors before doubling budgets.
- [Eng. post] Cost multiples: "agents typically use about 4× more tokens than chat interactions, and multi-agent systems use about 15× more tokens than chats." Multi-agent is a poor fit for domains "that require all agents to share the same context or involve many dependencies between agents." — [same](https://www.anthropic.com/engineering/multi-agent-research-system). → Harness: reserve full fan-out for theses that pass a cheap kill screen.
- [Eng. post] **Effort-scaling rules in the prompt:** "Simple fact-finding requires just 1 agent with 3-10 tool calls, direct comparisons might need 2-4 subagents with 10-15 calls each, and complex research might use more than 10 subagents with clearly divided responsibilities." — [same](https://www.anthropic.com/engineering/multi-agent-research-system). → Harness: copy these tiers into the orchestrator skill (quick check / comparison / full scan).
- [Eng. post] Delegation spec: "Each subagent needs an objective, an output format, guidance on the tools and sources to use, and clear task boundaries. Without detailed task descriptions, agents duplicate work, leave gaps, or fail to find necessary information." Their example: 3 subagents given "research the semiconductor shortage" duplicated each other's work. — [same](https://www.anthropic.com/engineering/multi-agent-research-system). → Harness: every collector brief should state objective, output schema (JSONL record), allowed sources and boundaries.
- [Eng. post] Observed failure modes: "spawning 50 subagents for simple queries, scouring the web endlessly for nonexistent sources, and distracting each other with excessive updates". Also "continuing when they already had sufficient results, using overly verbose search queries, or selecting incorrect tools". Human testers found agents "consistently chose SEO-optimized content farms over authoritative but less highly-ranked sources like academic PDFs or personal blogs." Small lead-prompt changes "unpredictably change how subagents behave." — [same](https://www.anthropic.com/engineering/multi-agent-research-system). → Harness: add explicit source-quality heuristics (primary sources such as IBGE, Receita Federal, Diário Oficial, company filings over SEO listicles) and stop conditions.
- [Eng. post] Speed: the lead "spins up 3-5 subagents in parallel rather than serially" and subagents "use 3+ tools in parallel". Together these "cut research time by up to 90% for complex queries." — [same](https://www.anthropic.com/engineering/multi-agent-research-system).
- [Eng. post] Self-improvement: a tool-testing agent rewrote flawed MCP tool descriptions, giving "a 40% decrease in task completion time for future agents using the new description." — [same](https://www.anthropic.com/engineering/multi-agent-research-system). → Harness: have Claude review failing transcripts and rewrite skill and script descriptions.
- [Eng. post] Search strategy: "start with short, broad queries, evaluate what's available, then progressively narrow focus". Extended and interleaved thinking "improved instruction-following, reasoning, and efficiency." — [same](https://www.anthropic.com/engineering/multi-agent-research-system).
- [Eng. post] Eval, part 1: "Start evaluating immediately with small samples… A prompt tweak might boost success rates from 30% to 80%… We started with a set of about 20 queries representing real usage patterns." — [same](https://www.anthropic.com/engineering/multi-agent-research-system). → Harness: a first eval set of about 20 historical opportunity cases (known winners and losers) is enough to start.
- [Eng. post] Eval, part 2, **LLM judge rubric**: "factual accuracy (do claims match sources?), citation accuracy (do the cited sources match the claims?), completeness…, source quality (did it use primary sources over lower-quality secondary sources?), and tool efficiency." Key result: "We experimented with multiple judges to evaluate each component, but found that **a single LLM call with a single prompt outputting scores from 0.0-1.0 and a pass-fail grade was the most consistent and aligned with human judgements**." — [same](https://www.anthropic.com/engineering/multi-agent-research-system). **Conflicts with** the Jan 2026 evals post, which recommends grading "each dimension with an isolated LLM-as-judge rather than using one to grade all dimensions" ([Demystifying evals](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)). → Harness: test both judge designs on your own labeled cases instead of assuming one.
- [Eng. post] Eval, part 3: "Human evaluation catches what automation misses" (hallucinations on unusual queries, source-selection bias). "Even in a world of automated evaluations, manual testing remains essential." — [same](https://www.anthropic.com/engineering/multi-agent-research-system).
- [Eng. post] Production: "Agents are stateful and errors compound." They built resume-from-failure, "retry logic and regular checkpoints", full tracing, and "rainbow deployments." Synchronous subagent execution "creates bottlenecks." — [same](https://www.anthropic.com/engineering/multi-agent-research-system). → Harness: versioned JSONL state and per-stage checkpoints allow resume after failure.
- [Eng. post] Appendix: "end-state evaluation rather than turn-by-turn analysis". For long horizons, "agents summarize completed work phases and store essential information in external memory". Subagent output goes to a filesystem "to minimize the 'game of telephone'": "Subagents call tools to store their work in external systems, then pass lightweight references back to the coordinator." — [same](https://www.anthropic.com/engineering/multi-agent-research-system). → Harness: collectors write evidence records to files and return paths. The judge reads the files, not the orchestrator's paraphrase.
- [Eng. post] Usage data: Research users "said that Claude helped them find business opportunities they hadn't considered". "Develop business growth and revenue generation strategies" was 8% of Research use cases (Clio). — [same](https://www.anthropic.com/engineering/multi-agent-research-system).

### Inferences
- For this harness, the "game of telephone" advice matters most for the blind judge. If the orchestrator summarizes the evidence into the judge's delegation prompt, its own lean leaks in. Passing file references keeps the judge blind.
- The 15× token multiple and "tokens explain 80% of variance" together imply budget tiers. Spend little on the kill screen and a lot only on theses that survive it.

### Gaps
- The post does not break out cost per query in dollars, and gives no numbers for citation-agent accuracy.
- The "open-source prompts in our Cookbook" (anthropics/claude-cookbooks) were not fetched in this pass.

## 3. Context engineering, harnesses for long-running agents, writing tools, Agent Skills

### Takeaway
Treat context as a finite "attention budget" and aim for "the smallest possible set of high-signal tokens." For long horizons, use compaction, structured note-taking, and sub-agents that return 1,000–2,000-token summaries. Long-running harnesses need an initializer, a JSON feature/status file, incremental progress, git commits and a progress log. Tools should be few, consolidated, token-efficient and prompt-engineered. Skills use three-level progressive disclosure: metadata (~100 tokens) → SKILL.md (<5k tokens, <500 lines) → bundled files and scripts. The description is the trigger.

### Cited Findings

**Context engineering (Sep 29, 2025)**
- [Eng. post] "Context rot: as the number of tokens in the context window increases, the model's ability to accurately recall information from that context decreases." Context is "a finite resource with diminishing marginal returns." Principle: "find the smallest possible set of high-signal tokens that maximize the likelihood of some desired outcome." — [Effective context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents). → Harness: keep CLAUDE.md and judge inputs lean, and pass evidence summaries plus paths rather than raw pages.
- [Eng. post] System prompts should sit at "the right altitude", between "brittle if-else hardcoded prompts" and "vague, high-level guidance". Start with a minimal prompt on the best model, then add instructions and examples based on observed failures. Use "diverse, canonical examples" rather than "a laundry list of edge cases." — [same](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents). → Harness: calibrate the judge with a few canonical worked verdicts, not an exhaustive rulebook.
- [Eng. post] "One of the most common failure modes we see is bloated tool sets… If a human engineer can't definitively say which tool should be used in a given situation, an AI agent can't be expected to do better." — [same](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents).
- [Eng. post] Agent definition updated to "LLMs autonomously using tools in a loop." "Just in time" retrieval: keep lightweight identifiers (paths, queries, links) and load data at runtime. Claude Code is hybrid: "CLAUDE.md files are naively dropped into context up front, while primitives like glob and grep allow it to navigate its environment and retrieve files just-in-time." — [same](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents). → Harness: the JSONL ledger plus grep/jq scripts is an idiomatic just-in-time store.
- [Eng. post] Long-horizon techniques. **Compaction** (Claude Code keeps summaries "plus the five most recently accessed files"; tool-result clearing is "one of the safest lightest touch forms of compaction"). **Structured note-taking** (e.g. NOTES.md, to-do lists). **Sub-agent architectures**, where each subagent "might explore extensively, using tens of thousands of tokens or more, but returns only a condensed, distilled summary of its work (often 1,000-2,000 tokens)." Choosing among them: "Compaction maintains conversational flow…; Note-taking excels for iterative development with clear milestones; Multi-agent architectures handle complex research and analysis." — [same](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents). → Harness: cap subagent returns at about 1–2k tokens, structured.
- [Eng. post] "'do the simplest thing that works' will likely remain our best advice." — [same](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents).

**Long-running harnesses (Nov 26, 2025, revised by Mar 2026; see §5)**
- [Eng. post] Two failure modes: the agent tries to "one-shot the app" and runs out of context mid-feature. Later, an agent "would look around, see that progress had been made, and declare the job done." The fix: an **initializer agent** writes `init.sh`, `claude-progress.txt` and an initial git commit, and a **coding agent** makes incremental progress each session and leaves structured updates. — [Effective harnesses for long-running agents](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents). → Harness: add an initializer skill that creates the opportunity's state files, and a "get your bearings" routine at each session start.
- [Eng. post] Feature list: "over 200 features", all initially `"passes": false`. Agents may only flip the status field ("It is unacceptable to remove or edit tests"). "**We landed on using JSON for this, as the model is less likely to inappropriately change or overwrite JSON files compared to Markdown files.**" — [same](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents). → Harness: keep hypothesis and validation-criteria status in JSON/JSONL, not Markdown, and guard it with a hook.
- [Eng. post] Premature "done": Claude tended "to mark a feature as complete without proper testing". Explicitly requiring end-to-end tests "as a human user would" (browser automation) "dramatically improved performance." — [same](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents). → Harness: in this domain the end-to-end test is contact with real buyers. Never mark a hypothesis "validated" on desk research alone.
- [Eng. post] Session start ritual: `pwd`, read the progress file and git log, read the feature list, pick the highest-priority failing item, run a basic smoke test first. — [same](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents).
- [Eng. post] Stress test with 16 parallel agents: "Over nearly 2,000 Claude Code sessions and $20,000 in API costs" they built a 100,000-line C compiler. Lessons: "the task verifier [must be] nearly perfect, otherwise Claude will solve the wrong problem". Avoid **context window pollution** ("print a few lines… log all important information to a file"; write `ERROR` plus the reason on one line so grep finds it). Mitigate **time blindness** with a `--fast` 1% or 10% sample. Keep READMEs and progress files updated. Use lock files in `current_tasks/` so parallel agents take different tasks. — [Building a C compiler with parallel Claudes](https://www.anthropic.com/engineering/building-c-compiler) (Feb 5, 2026). → Harness: scripts should print terse output and log details to files, and parallel collectors should claim tasks through lock files.

**Writing tools for agents (Sep 11, 2025)**
- [Eng. post] "More tools don't always lead to better outcomes." Avoid tools that "merely wrap existing software functionality or API endpoints". Consolidate instead, e.g. `search_contacts` rather than `list_contacts`, and `get_customer_context` in place of three separate calls. — [Writing effective tools for agents](https://www.anthropic.com/engineering/writing-tools-for-agents). → Harness: build Python scripts like `search_cnpj_by_cnae_and_city` rather than raw API dumps.
- [Eng. post] Namespacing (e.g. `asana_projects_search`). Prefix vs suffix naming "to have non-trivial effects" on evals. — [same](https://www.anthropic.com/engineering/writing-tools-for-agents).
- [Eng. post] Return meaningful context. Drop `uuid`, `mime_type` and similar fields. "Resolving arbitrary alphanumeric UUIDs to more semantically meaningful… language (or even a 0-indexed ID scheme) significantly improves Claude's precision." A `response_format` enum (`concise`/`detailed`) cut a Slack response from 206 to 72 tokens (about ⅓). — [same](https://www.anthropic.com/engineering/writing-tools-for-agents). → Harness: evidence records should use human-readable IDs (e.g. `opp-2026-017/ev-03`).
- [Eng. post] Token efficiency: "For Claude Code, we restrict tool responses to 25,000 tokens by default." Use pagination, filtering and truncation with steering messages, and "prompt-engineer your error responses to clearly communicate specific and actionable improvements." Web-search example: Claude was "needlessly appending 2025 to the tool's query parameter". — [same](https://www.anthropic.com/engineering/writing-tools-for-agents). → Harness: script errors should tell the agent what to do next.
- [Eng. post] Tool eval method: realistic multi-call tasks with verifiable outcomes. Avoid "overly strict verifiers". Track runtime, number of tool calls, tokens and tool errors. Use held-out test sets. "Most of the advice in this post came from repeatedly optimizing our internal tool implementations with Claude Code." Describe tools as you would to "a new hire", with unambiguous parameters (`user_id` not `user`). — [same](https://www.anthropic.com/engineering/writing-tools-for-agents).
- [Eng. post] Newer tool-platform features (Nov 2025). Tool Search Tool: "an 85% reduction in token usage"; MCP-eval accuracy "Opus 4 improved from 49% to 74%, and Opus 4.5 improved from 79.5% to 88.1%". Programmatic Tool Calling: "Average usage dropped from 43,588 to 27,297 tokens, a 37% reduction on complex research tasks". Tool Use Examples: "improved accuracy from 72% to 90% on complex parameter handling." — [Advanced tool use](https://www.anthropic.com/engineering/advanced-tool-use). Code execution with MCP (loading tool definitions from the filesystem) "reduces the token usage from 150,000 tokens to 2,000 tokens… 98.7%." — [Code execution with MCP](https://www.anthropic.com/engineering/code-execution-with-mcp). → Harness: having scripts filter large datasets before results reach context is the same idea, and a big saving.

**Agent Skills (Oct 16, 2025; open standard Dec 18, 2025)**
- [Eng. post] A skill is "a directory containing a SKILL.md file". YAML frontmatter holds the required `name` and `description`, which "the agent pre-loads… into its system prompt" (level 1). The full SKILL.md is level 2. Bundled files are "the third level (and beyond)". "The amount of context that can be bundled into a skill is effectively unbounded." Scripts run "without loading either the script or the PDF into context", which is deterministic. Update: "We've published Agent Skills as an open standard for cross-platform portability. (December 18, 2025)." — [Equipping agents with Agent Skills](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills). → Harness: judgment rubrics go in SKILL.md, long reference material (tax/regulatory notes, source catalogs) in bundled files, and scoring math in Python scripts.
- [Eng. post] Authoring guidance: "Start with evaluation". "When the SKILL.md file becomes unwieldy, split". "Pay special attention to the name and description". "Iterate with Claude". Security: "install skills only from trusted sources." — [same](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills).
- [Official doc] Level budgets: Level 1 metadata "~100 tokens per Skill". Level 2 "Under 5k tokens". Level 3+ "None until accessed… Scripts run through bash, and only their output enters context." — [Agent Skills overview](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/overview).
- [Official doc] Limits and description rules: `name` "Maximum 64 characters, lowercase letters/numbers/hyphens only… no reserved words" ("anthropic", "claude"). `description` "Maximum 1,024 characters". "**Always write in third person**". Say both what it does and when to use it, e.g. "Extract text and tables from PDF files… Use when working with PDF files or when the user mentions PDFs, forms, or document extraction." "Keep SKILL.md body under 500 lines". "Keep references one level deep from SKILL.md". Give files over 100 lines a table of contents. Use gerund names. Build "At least three evaluations". Use the "plan-validate-execute" pattern with verifiable intermediate outputs. — [Skill authoring best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices). → Harness: rewrite skill descriptions in third person with Portuguese and English trigger phrases, and keep bodies under 500 lines.
- [Official doc] "Default assumption: Claude is already very smart. Only add context Claude doesn't already have." "Set appropriate degrees of freedom" to match task fragility. — [same](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices).
- [Anthropic blog] skill-creator (Mar 3, 2026) distinguishes "**Capability uplift**" skills, which "may become less necessary as models improve", from "**Encoded preference**" skills, which are durable. It adds evals, a benchmark mode (pass rate, time, tokens), parallel isolated eval agents, "comparator agents for A/B comparisons… They judge outputs without knowing which is which", and description tuning, which "saw improved triggering on 5 out of 6 public skills." — [Improving skill-creator](https://claude.com/blog/improving-skill-creator-test-measure-and-refine-agent-skills). → Harness: the analista-imparcial and pesquisador-de-mercado skills are encoded-preference skills, so eval them for fidelity. The blind A/B comparator is the same pattern as the harness's blind judge.

### Inferences
- Anthropic's JSON-over-Markdown finding supports the harness's choice of JSONL for state. Markdown narrative is fine for human reports but should not hold status flags.
- In business validation, the "test end-to-end as a human user would" lesson means buyer contact is the only real end-to-end test, and desk research is the unit test.

### Gaps
- The Agent Skills open-standard spec at agentskills.io could not be fetched (egress blocked). Its field list is known only through the Claude Code docs' summary (six fields: `name`, `description`, `license`, `compatibility`, `metadata`, `allowed-tools`).
- No Anthropic post gives numbers on how many skills can coexist before triggering degrades. Only the listing-budget mechanics are documented (§4).

## 4. Claude Code features as of September 2026 (exact behavior and limits)

### Takeaway
As of September 2026, Claude Code has: custom commands merged into skills; subagents as Markdown+YAML files with about 18 frontmatter fields (including `tools`, `model`, `skills`, `memory`, `hooks`, `isolation`, `effort`, `omitClaudeMd`); 33 hook events with exit-2 blocking semantics and five handler types; a 5-level settings precedence; `claude -p` with JSON-schema output; the renamed Agent SDK; cloud **routines** (min 1-hour interval); session-scoped `/loop` (7-day expiry); `/goal`; **dynamic workflows** (script-orchestrated fan-out up to 1,000 agents per run); plugins with `claude plugin eval`; and experimental agent teams. **Subagents load the full CLAUDE.md hierarchy by default.** A blind judge must set `omitClaudeMd: true` and must never be a fork.

### Cited Findings

**CLAUDE.md / memory hierarchy**
- [Official doc] Load order runs from broad to specific, and files are concatenated, not overridden: Managed policy (`/etc/claude-code/CLAUDE.md` on Linux) → User `~/.claude/CLAUDE.md` → Project `./CLAUDE.md` or `./.claude/CLAUDE.md` → Local `./CLAUDE.local.md`. Files above the cwd load at launch. Subdirectory CLAUDE.md files load on demand when Claude reads files there. — [Memory](https://code.claude.com/docs/en/memory).
- [Official doc] "target under 200 lines per CLAUDE.md file. Longer files consume more context and reduce adherence." `@path` imports are allowed, "maximum depth of four hops", but imported files still load at launch. Block-level HTML comments are stripped before injection. Files up to 4 MiB load in full. — [same](https://code.claude.com/docs/en/memory). → Harness: move procedures out of CLAUDE.md into skills, and use `<!-- -->` for maintainer notes.
- [Official doc] "CLAUDE.md content is delivered as a user message after the system prompt, not as part of the system prompt itself… there's no guarantee of strict compliance." "To block an action regardless of what Claude decides, use a PreToolUse hook." For system-prompt-level instructions use `--append-system-prompt`. — [same](https://code.claude.com/docs/en/memory). → Harness: invariants such as "never edit the evidence ledger in place" must be hooks, not CLAUDE.md prose.
- [Official doc] `.claude/rules/*.md` files are modular. Rules without `paths` load at launch. Rules with `paths:` globs load only when matching files are touched. — [same](https://code.claude.com/docs/en/memory). → Harness: path-scope rules, e.g. `research/notas/**` gets citation rules and `scripts/**/*.py` gets coding rules.
- [Official doc] Auto memory: Claude writes `user`/`feedback`/`project`/`reference` notes to `~/.claude/projects/<project>/memory/`. The `MEMORY.md` index loads its "first 200 lines… or the first 25KB". Auto memory is "machine-local… not shared across machines or cloud environments", and "isn't loaded into subagents" except forks. — [same](https://code.claude.com/docs/en/memory). → Harness: don't rely on auto memory for harness state. Routines and cloud sessions won't see it, so versioned repo files are right.
- [Official doc] AGENTS.md is read natively (v2.1.277+), but by default only when no CLAUDE.md exists on the path. — [same](https://code.claude.com/docs/en/memory).

**Subagents**
- [Official doc] Definition: Markdown file with YAML frontmatter, where the body is the system prompt. "Only `name` and `description` are required." Scopes by priority: Managed (1) > `--agents` CLI JSON (2) > `.claude/agents/` (3) > `~/.claude/agents/` (4) > plugin `agents/` (5). Scanned recursively, with identity from `name` only. Hot-reloaded within seconds. — [Subagents](https://code.claude.com/docs/en/sub-agents).
- [Official doc] Frontmatter fields: `name`, `description`, `tools` (allowlist; `Agent(worker, researcher)` restricts spawnable types), `disallowedTools`, `model` (`sonnet`/`opus`/`haiku`/`fable`/full ID/`inherit`), `permissionMode`, `maxTurns` (returns output "marked as partial"), `skills` (preload full content), `mcpServers`, `hooks`, `memory` (`user`/`project`/`local`), `background`, `omitClaudeMd` (v2.1.271+), `effort` (`low`…`max`), `isolation: worktree`, `color`, `initialPrompt`, `experimental.cacheTtl`. **Unknown fields are silently ignored.** Files with no name or broken YAML are skipped without notice (check with `claude plugin validate .claude/agents`). — [same](https://code.claude.com/docs/en/sub-agents). → Harness: add a CI check that validates agent frontmatter, since typos fail silently.
- [Official doc] **What a non-fork subagent sees at startup:** its own system prompt plus environment details ("not the Claude Code system prompt"), the delegation message Claude writes, **"CLAUDE.md files: every level of the CLAUDE.md hierarchy the main conversation loads"**, a git status snapshot, preloaded skills, and a sibling roster (only if it has `SendMessage`). "It doesn't see your conversation history." Output style and the main auto memory never reach it. `omitClaudeMd: true` launches it "without the user, project, and local CLAUDE.md files." — [same](https://code.claude.com/docs/en/sub-agents). → Harness: **the blind judge and advocate/skeptic need `omitClaudeMd: true`** if CLAUDE.md mentions the thesis, prior verdicts or the owner's hopes. Omit `SendMessage` so they don't get a roster or cross-talk. Note that git status (recent commits named after opportunities) always leaks and "You can't change which subagents receive git status."
- [Official doc] **Forks** "inherit the entire conversation… This drops the input isolation that subagents otherwise provide." Fork mode is on by default in interactive sessions (v2.1.232+) and off in `-p`/SDK. A skill's `context: fork` is *not* a conversation fork. — [same](https://code.claude.com/docs/en/sub-agents). → Harness: never run the judge as a fork. Use a named custom agent type.
- [Official doc] Limits: nesting "up to three layers below the main conversation" by default (`CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH`). The default was 5 layers in v2.1.172–v2.1.216 and 1 in v2.1.217–218. **Concurrent limit: 20 running subagents** (`CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS`), and "There's no limit on the total number of subagents". Combined descriptions over 15,000 tokens trigger a startup warning. — [same](https://code.claude.com/docs/en/sub-agents).
- [Official doc] Model resolution order: per-invocation `model` param → frontmatter `model` → `CLAUDE_CODE_SUBAGENT_MODEL` → main model. Before v2.1.251 the env var came first. Subagents inherit the session's extended-thinking setting (v2.1.198+), and "There is no per-subagent thinking setting." — [same](https://code.claude.com/docs/en/sub-agents). → Harness: pin the judge's model in frontmatter. The orchestrator can still override it per call, so say so in its instructions.
- [Official doc] Background subagents get a reduced built-in tool set (Read, Grep, Glob, Bash, Edit, Write, WebFetch, WebSearch, Skill, etc., plus all MCP tools) and surface permission prompts in the main session. Subagents never get `AskUserQuestion`. Transcripts are stored at `~/.claude/projects/{project}/{sessionId}/subagents/agent-{id}.jsonl` and deleted after `cleanupPeriodDays` (30 by default). — [same](https://code.claude.com/docs/en/sub-agents). → Harness: copy judge transcripts into the repo if they are audit evidence.
- [Official doc] Subagent output scanning (v2.1.210+) escapes injected `<system-reminder>`/`Human:` text and marks reports as carrying "no authority from you." Messages from other agents never count as user approval. — [same](https://code.claude.com/docs/en/sub-agents).
- [Official doc] Persistent `memory:` gives the agent a directory (`project` scope → `.claude/agent-memory/<name>/`) whose `MEMORY.md` (first 200 lines/25KB) is injected. — [same](https://code.claude.com/docs/en/sub-agents). → Harness: be careful. Judge memory of past verdicts can bias future blind judgments, so consider leaving memory off for the judge.

**Skills vs slash commands (unified)**
- [Official doc] "**Custom commands have been merged into skills.** A file at `.claude/commands/deploy.md` and a skill at `.claude/skills/deploy/SKILL.md` both create `/deploy` and work the same way." Claude Code skills follow the Agent Skills open standard, with extensions. — [Skills](https://code.claude.com/docs/en/skills).
- [Official doc] Skill frontmatter (all optional; `description` recommended): `name`, `description`, `when_to_use`, `argument-hint`, `arguments`, `disable-model-invocation`, `user-invocable`, `allowed-tools` (a per-turn pre-approval, "does not restrict"), `disallowed-tools`, `model`, `effort`, `context: fork`, `agent`, `background`, `hooks`, `paths`, `shell`, `metadata`, `license`, `compatibility`. "The combined `description` and `when_to_use` text is truncated at 1,536 characters in the skill listing." — [same](https://code.claude.com/docs/en/skills). **Discrepancy:** the platform spec caps `description` at 1,024 characters ([best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)).
- [Official doc] **Skills synced to claude.ai (needed for Cowork, cloud sessions and routines) may only use `name`, `description`, `license`, `compatibility`, `metadata`, `allowed-tools`.** Any other key causes a hard error: "Unexpected key(s) in SKILL.md frontmatter". — [same](https://code.claude.com/docs/en/skills). → Harness: skills meant to run in routines must avoid CC-only fields such as `context`, `hooks` and `when_to_use`.
- [Official doc] Invocation control: `disable-model-invocation: true` means only the user can invoke the skill, its description stays out of context, and it cannot be preloaded or run from scheduled tasks. `user-invocable: false` means only Claude can invoke it. — [same](https://code.claude.com/docs/en/skills). → Harness: side-effecting skills (sending outreach to real buyers, publishing landing pages, spending money) should be `disable-model-invocation: true`.
- [Official doc] Lifecycle: invoked skill content "stays in context across turns" and is not re-read. After compaction, the most recent invocation of each skill is re-attached, "keeping the first 5,000 tokens of each… combined budget of 25,000 tokens." The skill listing budget "scales at 1% of the model's context window", and descriptions of least-used skills get dropped first. — [same](https://code.claude.com/docs/en/skills). → Harness: put a skill's critical rules in its first 5k tokens.
- [Official doc] `context: fork` runs the skill as the task of a subagent of type `agent`, which "doesn't see your conversation history". It still loads CLAUDE.md per that agent's rules. Explore/Plan agent types skip CLAUDE.md and git status. It runs in the background by default, but waits in `-p`/SDK. — [same](https://code.claude.com/docs/en/skills).
- [Official doc] Skill evaluation: compare runs with and without the skill in fresh sessions. The skill-creator plugin stores cases in `evals/evals.json`, runs isolated subagents per case, does blind A/B between versions, and tunes descriptions with should- and should-not-trigger prompts. `claude plugin eval` gates CI on score, including a `tool_used: Skill` grader for trigger rate. — [Skills](https://code.claude.com/docs/en/skills); [Plugin evals](https://code.claude.com/docs/en/plugin-evals).

**Hooks**
- [Official doc] 33 events, including `SessionStart`, `Setup`, `UserPromptSubmit`, `UserPromptExpansion`, `PreToolUse`, `PermissionRequest`, `PermissionDenied`, `PostToolUse`, `PostToolUseFailure`, `PostToolBatch`, `Notification`, `MessageDisplay`, `SubagentStart`, `SubagentStop`, `TaskCreated`, `TaskCompleted`, `Stop`, `StopFailure`, `TeammateIdle`, `InstructionsLoaded`, `ConfigChange`, `CwdChanged`, `DirectoryAdded`, `FileChanged`, `WorktreeCreate/Remove`, `PreCompact`, `PostCompact`, `Pre/PostModelSwitch`, `Elicitation(Result)`, `SessionEnd`. — [Hooks reference](https://code.claude.com/docs/en/hooks).
- [Official doc] Five handler types: `command`, `http`, `mcp_tool`, `prompt` (single-turn model judgment, 30 s default timeout), `agent` (a subagent with Read/Grep/Glob; "experimental", 60 s default). All matching hooks run in parallel. — [same](https://code.claude.com/docs/en/hooks).
- [Official doc] **Blocking semantics:** "exit code 2 is the only exit code that blocks through the code alone… Claude Code treats exit code 1 as a non-blocking error and proceeds." Blockable events: PreToolUse, UserPromptSubmit, UserPromptExpansion, Stop, SubagentStop, TeammateIdle, TaskCreated, TaskCompleted, ConfigChange, PostToolBatch, PreCompact, PreModelSwitch, Elicitation, and the Worktree events. PostToolUse cannot block, but exit 2 "Shows stderr to Claude". **A timed-out PreToolUse command hook does not block**, so "don't count on a stalled hook to act as a gate." — [same](https://code.claude.com/docs/en/hooks). → Harness: validation scripts must `exit 2`. A Python traceback (exit 1) silently lets the action through.
- [Official doc] Stop/SubagentStop receive `stop_hook_active` and `last_assistant_message`. SubagentStop also gets `agent_type` and `agent_transcript_path`. "Claude Code overrides the hook and ends the turn after 8 consecutive blocks." — [same](https://code.claude.com/docs/en/hooks). → Harness: a **SubagentStop hook matched on the judge's `agent_type` can validate the verdict JSON schema** (probabilities, cited evidence IDs) and force a retry.
- [Official doc] Hook locations: `~/.claude/settings.json`, `.claude/settings.json` (committable), `.claude/settings.local.json`, managed, plugin `hooks/hooks.json`, skill frontmatter (active "for the rest of the session", with `once: true` available), subagent frontmatter (active only while that subagent runs; `Stop` becomes `SubagentStop`). Settings hooks also fire inside subagents, with `agent_id`/`agent_type` in the input. Cloud sessions don't read `~/.claude/settings.json`. — [same](https://code.claude.com/docs/en/hooks). → Harness: put invariant hooks in the committed `.claude/settings.json` so routines and cloud sessions get them.
- [Official doc] Hooks vs permissions: "Hook decisions don't bypass permission rules" (deny/ask still apply), but "A hook that exits with code 2 stops the tool call before permission rules are evaluated." The `if` filter "is best-effort, use the permission system… to enforce a hard allow or deny." — [Permissions](https://code.claude.com/docs/en/permissions); [Hooks](https://code.claude.com/docs/en/hooks).

**Settings / permissions**
- [Official doc] Precedence, highest first: "managed settings, command line, project local, shared project, user." — [Settings](https://code.claude.com/docs/en/settings).
- [Official doc] "Rules are evaluated in order: deny, then ask, then allow… An allow rule can't carve an exception out of a deny rule." Modes: `default` (labeled Manual), `acceptEdits`, `plan`, `auto` (classifier-checked), `dontAsk` (auto-deny anything that would prompt), `bypassPermissions`. — [Permissions](https://code.claude.com/docs/en/permissions). → Harness: in unattended runs use `dontAsk` or `auto` plus explicit allow rules, and deny rules for anything that contacts buyers or spends money.
- [Eng. post] Auto mode rationale: "Claude Code users approve 93% of permission prompts". The classifier pipeline had "8.5% FPR" at stage 1 and "0.4% FPR, 17% FNR" end to end. — [Claude Code auto mode](https://www.anthropic.com/engineering/claude-code-auto-mode) (Mar 25, 2026). → Harness: auto mode misses about 1 in 6 risky actions (17% FNR), so irreversible external actions still need deny rules or hooks.

**Headless (`claude -p`) and Agent SDK**
- [Official doc] `claude -p "…" --output-format json` returns `total_cost_usd` and per-model cost. `--json-schema '<schema>'` puts schema-conformant output in `structured_output`. `stream-json --verbose` streams events. `--allowedTools` uses permission-rule syntax. `--bare` "skip[s] auto-discovery of hooks, skills, custom commands, subagents, plugins, MCP servers, auto memory, and CLAUDE.md" and "is the recommended mode for scripted and SDK calls, and will become the default for `-p` in a future release." Without `--bare`, `-p` runs project hooks and MCP "even in a folder you've never trusted". — [Headless](https://code.claude.com/docs/en/headless). → Harness: `claude -p --json-schema` is a clean way for Python scripts to call an isolated judge and log cost. **Beware:** `--bare` also drops your validation hooks and skills, so pass them explicitly or skip `--bare`.
- [Official doc] Fan-out pattern: "Loop through tasks calling `claude -p` for each. Use `--allowedTools` to scope permissions". `/batch` splits changes across 5–30 subagents in worktrees. — [Best practices](https://code.claude.com/docs/en/best-practices).
- [Official doc] The Agent SDK is "a library that runs the Claude Code binary" in Python and TypeScript, with built-in tools, hooks, subagents, MCP, permissions, sessions, and "Skills, commands, and memory… Load automatically from your project's `.claude/`". Third-party products may not offer claude.ai login. — [Agent SDK overview](https://code.claude.com/docs/en/agent-sdk/overview).
- [Anthropic blog] **Renamed (flag):** "we're renaming the Claude Code SDK to the Claude Agent SDK" (Sep 29, 2025). Loop: "gather context -> take action -> verify work -> repeat". Verification ranking: rules-based feedback is best. LLM-as-judge "is generally not a very robust method, and can have heavy latency tradeoffs". — [Building agents with the Claude Agent SDK](https://claude.com/blog/building-agents-with-the-claude-agent-sdk). → Harness: turn every judgment criterion you can into a deterministic rule-check script, and keep LLM judgment for what is truly fuzzy.
- [Official doc] Tool rename (flag): "In version 2.1.63, the Task tool was renamed to Agent. Existing `Task(...)` references… still work as aliases." — [Subagents](https://code.claude.com/docs/en/sub-agents).

**Scheduled / recurring execution and cloud sessions**
- [Official doc] Three options. **Routines** run in the cloud: no machine or session needed, fresh clone each run, connectors per task, no permission prompts, **minimum interval 1 hour**. **Desktop tasks** run on your machine with local files, 1-minute minimum. **`/loop`** is session-scoped, 1-minute minimum, and "Recurring tasks automatically expire 7 days after creation." — [Scheduled tasks](https://code.claude.com/docs/en/scheduled-tasks).
- [Official doc] Routines are a research preview. "A routine is a saved Claude Code configuration: a prompt, one or more repositories, and a set of connectors." Triggers: schedule (hourly/daily/weekdays/weekly, custom cron via `/schedule update`, one-off), API (HTTP POST with bearer token), GitHub events. Available on Pro/Max/Team/Enterprise. "Claude pushes its work to branches prefixed with `claude/`". "Routines have a daily cap on how many runs can start per account". One-off runs don't count toward it. Local `claude mcp add` servers are not available unless added as claude.ai connectors or in a committed `.mcp.json`. The Default environment's network is "Trusted" (allowlist only; others get `403 host_not_allowed`), so add Custom domains. — [Routines](https://code.claude.com/docs/en/routines). → Harness: a nightly routine can re-scan signals and append to JSONL on a `claude/` branch. Brazilian data-source domains must be added to the environment allowlist.
- [Official doc] `/goal <condition>`: "After each turn, a small fast model checks whether the condition holds". One goal per session. "Completion is decided by a fresh model rather than the one doing the work." — [Goal](https://code.claude.com/docs/en/goal).

**Dynamic workflows, agent teams, plugins**
- [Official doc] A dynamic workflow is "a JavaScript script that orchestrates many subagents". "Intermediate results stay in script variables instead of landing in Claude's context." It can "have independent agents adversarially review each other's findings." Limits: no mid-run user input, no direct filesystem or shell access from the script, no `import()`, "Up to 16 concurrent agents by default" (env var, 1–256), 4,096 items per `parallel()`/`pipeline()`, "1,000 agents total per run". A "Large workflow" warning appears above 25 agents or a projected 1.5M tokens. Runs are resumable within the session. Saved to `.claude/workflows/` and run as `/<name>`. Bundled `/deep-research`. — [Workflows](https://code.claude.com/docs/en/workflows). → Harness: the advocate → skeptic → blind-judge pipeline can be written as a saved workflow, which makes the orchestration deterministic, repeatable and resumable. Human checkpoints must fall *between* workflow runs.
- [Official doc] Agent teams: "experimental and disabled by default" (`CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1`). A lead plus teammates with their own contexts who "share and challenge each other's findings". They "use significantly more tokens". — [Agent teams](https://code.claude.com/docs/en/agent-teams).
- [Official doc] Plugins bundle skills, agents, hooks and MCP (`.claude-plugin/plugin.json`), namespaced as `/plugin-name:skill`. "Start with standalone configuration in `.claude/`… then convert to a plugin when you're ready to share." Plugin subagents ignore `hooks`, `mcpServers` and `permissionMode`. — [Plugins](https://code.claude.com/docs/en/plugins); [Subagents](https://code.claude.com/docs/en/sub-agents).

**Official best-practices document**
- [Official doc] The core constraint: "Claude's context window fills up fast, and performance degrades as it fills." #1 practice: "Give Claude a way to verify its work", with four escalating gates: in-prompt check, `/goal`, a Stop hook ("deterministic gate"), and "a verification subagent… so the agent doing the work isn't the one grading it." Also: "Have Claude show evidence rather than asserting success." — [Best practices](https://code.claude.com/docs/en/best-practices).
- [Official doc] Adversarial review: "A reviewer running in a fresh subagent context sees only the diff and the criteria you give it, not the reasoning that produced the change." Caveat: "**A reviewer prompted to find gaps will usually report some, even when the work is sound… Tell the reviewer to flag only gaps that affect correctness or the stated requirements.**" — [same](https://code.claude.com/docs/en/best-practices). → Harness: the skeptic will always find objections. Have the judge weigh them by materiality, not count.
- [Official doc] Failure patterns: kitchen-sink session, "After two failed corrections, `/clear`", over-specified CLAUDE.md ("Ruthlessly prune… convert it to a hook"), trust-then-verify gap, infinite exploration. — [same](https://code.claude.com/docs/en/best-practices).
- [Official doc] Context cost by feature: CLAUDE.md is full content on every request. Skills: descriptions every request, full content when used. MCP: tool names, with schemas on demand. Subagents are isolated. Hooks cost "Zero, unless hook returns additional context." — [Features overview](https://code.claude.com/docs/en/features-overview).

### Inferences
- The biggest risk found for the harness design: **isolation is weaker than it looks by default.** Subagents inherit CLAUDE.md and a git-status snapshot, forks inherit everything, and the orchestrator writes the delegation prompt. A truly blind judge needs `omitClaudeMd: true`, no `SendMessage`, file-path inputs instead of orchestrator summaries, a pinned model, and ideally a run via `claude -p --bare --json-schema` or a workflow agent. Git-status leakage can't be switched off inside Claude Code, so an external `claude -p` call from a neutral directory gives the strongest isolation.
- Hooks are the only deterministic enforcement layer. Validation must `exit 2`, and hooks must live in committed settings to reach routines and cloud sessions.
- Routines plus committed JSONL state plus `claude/` branches fit a "nightly signal scan, human reviews the PR" loop. Routine skills must use only the six spec fields.

### Gaps
- I did not check which Claude Code version the user runs. Many cited behaviors require specific versions: `omitClaudeMd` v2.1.271+, `claude plugin validate` for agents dirs v2.1.233+, workflow concurrency env var v2.1.269+, AGENTS.md v2.1.277+.
- The routine daily run cap number is not stated in the docs, only shown in the UI.
- Cloud environment expiry and session duration limits were not captured.
- The agent-teams limitations section was not read in full.

## 5. Newer (2025–2026) posts that supersede or revise earlier guidance

### Takeaway
The main 2026 revision: **"every component in a harness encodes an assumption about what the model can't do on its own"**, and those assumptions go stale. Context resets (needed for Sonnet 4.5's "context anxiety") became "dead weight" on Opus 4.5. Sprint decomposition was dropped on Opus 4.6. Separating generator from evaluator is the lasting lever, because "tuning a standalone evaluator to be skeptical turns out to be far more tractable than making a generator critical of its own work." For evals: start with 20–50 tasks from real failures, use balanced sets, and read transcripts.

### Cited Findings
- [Eng. post] Self-evaluation bias: "When asked to evaluate work they've produced, agents tend to respond by confidently praising the work—even when… the quality is obviously mediocre." "**Separating the agent doing the work from the agent judging it proves to be a strong lever**… tuning a standalone evaluator to be skeptical turns out to be far more tractable than making a generator critical of its own work." — [Harness design for long-running apps](https://www.anthropic.com/engineering/harness-design-long-running-apps) (Mar 24, 2026). → Harness: this directly supports keeping advocate and judge as separate agents.
- [Eng. post] "Out of the box, Claude is a poor QA agent… I watched it identify legitimate issues, then talk itself into deciding they weren't a big deal and approve the work anyway." The fix was an iterative loop: "read the evaluator's logs, find examples where its judgment diverged from mine, and update the QA's prompt". The evaluator was calibrated "using few-shot examples with detailed score breakdowns", which "reduced score drift across iterations." Each criterion had "a hard threshold, and if any one fell below it, the sprint failed." — [same](https://www.anthropic.com/engineering/harness-design-long-running-apps). → Harness: calibrate the judge with scored exemplar verdicts, use per-criterion hard thresholds (kill criteria), and audit judge logs for "talked itself out of it" behavior.
- [Eng. post] Criteria wording steers output: "Including phrases like 'the best designs are museum quality' pushed designs toward a particular visual convergence." — [same](https://www.anthropic.com/engineering/harness-design-long-running-apps). → Harness: word the rubric neutrally, e.g. avoid "unicorn potential" language that biases the advocate or the judge.
- [Eng. post] Planner / generator / evaluator architecture. Before each sprint the generator and evaluator negotiated a "**sprint contract**: agreeing on what 'done' looked like… before any code was written". "Communication was handled via files." — [same](https://www.anthropic.com/engineering/harness-design-long-running-apps). → Harness: fix validation criteria per opportunity (a "validation contract") *before* collecting evidence, to stop goalposts moving.
- [Eng. post] Cost: Solo run "20 min / $9" vs full harness "6 hr / $200". "The harness was over 20x more expensive, but the difference in output quality was immediately apparent" (the solo app's core feature was broken). V2 harness on Opus 4.6: "3 hr 50 min / $124.70". — [same](https://www.anthropic.com/engineering/harness-design-long-running-apps).
- [Eng. post] **Supersedes Nov 2025 context resets:** "Opus 4.5 largely removed that behavior on its own, so I was able to drop context resets from this harness entirely", relying on "the Claude Agent SDK's automatic compaction". Sprint construct removed on Opus 4.6. "**the evaluator is not a fixed yes-or-no decision. It is worth the cost when the task sits beyond what the current model does reliably solo.**" Simplify "removing one component at a time". — [same](https://www.anthropic.com/engineering/harness-design-long-running-apps). → Harness: after each model upgrade, ablate stages one at a time. The skeptic and judge may be dispensable for easy screens but essential for close calls.
- [Eng. post] Managed Agents (Apr 8, 2026): "harnesses encode assumptions about what Claude can't do on its own… those assumptions need to be frequently questioned because they can go stale." On context resets: "The resets had become dead weight." Architecture virtualizes the **session** ("the append-only log of everything that happened"), the **harness**, and the **sandbox**, and "The session is not Claude's context window". Decoupling cut "p50 TTFT… roughly 60% and p95… over 90%". — [Scaling Managed Agents](https://www.anthropic.com/engineering/managed-agents). → Harness: an append-only JSONL event log as the source of truth, apart from any context window, is the same pattern Anthropic productized.
- [Eng. post] Evals (Jan 9, 2026): "20-50 simple tasks drawn from real failures is a great start". "A good task is one where two domain experts would independently reach the same pass/fail verdict". Create a reference solution per task. "**Build balanced problem sets**… Test both the cases where a behavior should occur and where it shouldn't. One-sided evals create one-sided optimization." Isolate trials, since "Claude gaining an unfair advantage… by examining the git history from previous trials". Metrics: "pass@k" (at least one of k succeeds) vs "pass^k" (all k succeed; e.g. 75% per trial → "(0.75)³ ≈ 42%"). Give the LLM judge "a way out… return 'Unknown'". ### Inferences
- The 2026 guidance endorses the harness's core bet (separate judge, tuned toward skepticism, calibrated with exemplars). It adds three requirements: (1) a pre-agreed validation contract per opportunity; (2) periodic ablation after model upgrades; (3) injection hygiene for persisted state.
- There is an open conflict about judge structure: one holistic call (Jun 2025) vs isolated per-dimension judges (Jan 2026). Neither post tested debate setups (advocate vs skeptic feeding a judge). The harness should settle it empirically on its own labeled cases.

### Gaps
- The Claude blog post "A harness for every task: dynamic workflows in Claude Code" (linked from the Agent SDK docs) could not be fetched. claude.dev is blocked by the egress proxy. Its claims are not covered here.
- No Anthropic source directly evaluates **advocate/skeptic debate followed by a blind judge**. The nearest analogues are generator/evaluator separation, voting, adversarial review subagents, workflow cross-review, and agent-teams "challenge each other's findings". There is no published evidence that debate beats a single calibrated skeptical evaluator.
- No Anthropic guidance is specific to business-opportunity discovery or market validation beyond the Research-feature usage statistics.
