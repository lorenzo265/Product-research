## 1. Cognition — "Don't Build Multi-Agents" (Walden Yan, June 2025) and its 2026 update

### Takeaway
Cognition's 2025 argument (share full context; actions carry implicit decisions, so parallel writers produce incoherent results) has not been retracted but was sharpened in ~April 2026 into "writes stay single-threaded; extra agents contribute intelligence, not actions," with three production patterns (clean-context review loop, "smart friend," map-reduce-and-manage) and unstructured swarms dismissed. Our design (read-only researchers, isolated reviewers, centralized writes) is essentially the pattern Cognition now endorses.

### Cited Findings
- **Principle 1: "Share context, and share full agent traces, not just individual messages."** Subagents that get only a task description lack the context behind it. [PRACT-OPINION] — [Cognition, Don't Build Multi-Agents](https://cognition.com/blog/dont-build-multi-agents) (via search excerpt). → A task brief for a researcher subagent must carry the *why* (thesis, prior decisions, exclusions), not just the query.
- **Principle 2: "Actions carry implicit decisions, and conflicting decisions carry bad results."** Subagents that can't see each other's work act on conflicting unstated assumptions. [PRACT-OPINION] — [Cognition](https://cognition.com/blog/dont-build-multi-agents); summarized in [Jason Zhou on X](https://x.com/jasonzhou1993/status/1933484175140794639). → Never let two subagents write to the same artifact/state file; any output that embeds a decision (ranking, verdict, scope cut) must be made in one thread.
- **Flappy Bird example:** one subagent built a Super Mario–style background, another built a bird that didn't fit the game, because neither saw the other's implicit design choices. [PRACT-OPINION, illustrative anecdote] — [Cognition](https://cognition.com/blog/dont-build-multi-agents) (via search excerpt). → Parallel "writers" of pieces of one deliverable (e.g., sections of one opportunity memo) will drift in style and assumptions; merge must be done by one agent with full context.
- **What they recommend instead:** a single-threaded linear agent where context is continuous; for very long tasks, add a model whose job is to compress history into key details, events and decisions. They note that, as a consequence of Principle 2, most real multi-agent setups are limited to "read-only" subagents (web search, code search), and observed that Claude Code subagents do not work in parallel with the main agent and are usually tasked with answering a question, not writing code. [PRACT-OPINION] — [Cognition](https://cognition.com/blog/dont-build-multi-agents) (read-only point via search excerpt; compression-model and Claude Code points [not fetched; from primary text]). → Our "researchers answer questions, main session decides and writes" split matches the one form Cognition accepted even in 2025.
- **2026 update, "Multi-Agents: What's Actually Working" (Walden Yan, ~April 2026; date inferred from the X post ID):** "multi-agent systems work best today when writes stay single-threaded and the additional agents contribute intelligence rather than actions." Described as a sharpening, not a retraction, of the 2025 post. [PRACT-OPINION / PROD-REPORT without metrics] — [Cognition blog](https://cognition.com/blog/multi-agents-working); [X article](https://x.com/walden_yan/article/2047054401341370639); secondary: [Level Up Coding, Apr 2026](https://levelup.gitconnected.com/where-agentic-ai-goes-from-here-775e7c517c6b?gi=a8fb25bfb55a). → The 2025 "don't build multi-agents" headline is **superseded**; cite the 2026 principle instead.
- **Three working patterns:** (a) *Code-Review Loop* — "a clean-context reviewer catches bugs the coder can't see"; (b) *Smart Friend* — a frontier model consulted by the primary catches subtleties; works when both are strong, while a weak primary + strong friend "is still an open problem, and we think it's a training one"; (c) *Map-reduce-and-manage* — a manager splits work, children execute, manager synthesizes; "a manager coordinates scope across child agents without fragmenting decisions." Unstructured swarms ("arbitrary networks of agents negotiating") are "mostly a distraction." [PRACT-OPINION] — [Cognition](https://cognition.com/blog/multi-agents-working); [note.com summary](https://note.com/masa_wunder/n/n495e03a4cf7d?hl=en). → Isolated skeptic/advocate reviewers are a direct analogue of the clean-context reviewer; keep the judge as the single "manager" that decides; do not add peer-to-peer debate between subagents.
- **Open problems are "communication problems":** how agents share context, escalate decisions, and surface discoveries without overwhelming each other; making manager/children feel "as coherent as a single agent" is ongoing 2026 work. Fragmentation arises when parallel agents make conflicting implicit choices (style, patterns, edge cases). [PRACT-OPINION] — [Cognition](https://cognition.com/blog/multi-agents-working). → Standardize subagent return formats (schema'd JSONL findings with evidence + confidence) so the manager can merge without re-reading everything, and give subagents an explicit "escalate/uncertain" field.
- Devin itself calls a DeepWiki subagent for codebase context (read-only intelligence). [PRACT-OPINION] — [search excerpt citing Cognition](https://cognition.com/blog/multi-agents-working). → Read-only retrieval subagents are the lowest-risk multi-agent use.
- Rebuttal/debate context: the post triggered a public debate; Anthropic published a counter-case the next day, and LangChain's Harrison Chase reconciled the two (see §6). [Secondary commentary] — [search excerpt](https://medium.com/@maureesewilliams/the-agent-architecture-wars-why-two-ai-giants-completely-disagree-on-multi-agent-systems-d19a53364200); [Jason Liu, "Why Cognition does not use multi-agent systems" (Sep 2025)](https://jxnl.co/writing/2025/09/11/why-cognition-does-not-use-multi-agent-systems/).

### Inferences
- Cognition's position and Anthropic's research-system position converge on the same boundary: parallelism for *reading/intelligence*, single thread for *writing/deciding*. The live disagreement is now about how far map-reduce-and-manage can be pushed, not whether multi-agent works at all.
- The "clean-context reviewer" is the strongest production endorsement of our advocate/skeptic isolation: the value comes precisely from *not* sharing the author's context (the reverse of Principle 1). So Principle 1 applies to executors, while reviewers benefit from deliberate context withholding.

### Gaps
- Could not fetch either Cognition post directly; no quantitative results (bug-catch rates, cost) from the 2026 post were retrievable — likely none were published, but unverified.
- No independent replication of Cognition's claims found.

## 2. HumanLayer — "12-Factor Agents" (Dex Horthy)

### Takeaway
12-Factor Agents is an opinion framework, not an empirical study, arguing that good production agents are "mostly deterministic code, with LLM steps sprinkled in," with owned prompts, owned context, small focused agents (3–10, maybe 20 steps), human contact as a tool call, and one serializable event thread as the single source of truth. It aligns closely with a harness built on Python scripts + versioned JSONL state.

### Cited Findings
- The 12 factors (+ appendix): (1) natural language → tool calls; (2) own your prompts; (3) own your context window; (4) tools are just structured outputs; (5) unify execution state and business state; (6) launch/pause/resume with simple APIs; (7) contact humans with tool calls; (8) own your control flow; (9) compact errors into context window; (10) small, focused agents; (11) trigger from anywhere; (12) make your agent a stateless reducer; (13, appendix) pre-fetch all context you might need. [PRACT-OPINION] — [12-Factor Agents README (fetched)](https://github.com/humanlayer/12-factor-agents). → Useful as a checklist for the harness; factors 5, 7, 8, 10, 13 map directly onto our design.
- On frameworks: builders reach ~80% quality with a framework, then must "reverse-engineer the framework" to reach production quality; successful production agents are "mostly deterministic code, with LLM steps sprinkled in at just the right points." [PRACT-OPINION] — [README (fetched)](https://github.com/humanlayer/12-factor-agents). → Keep orchestration (stage order, gating, state writes) in Python scripts/hooks; use LLM calls only for judgment steps.
- **Own your context window:** "Everything is context engineering"; "LLMs are stateless functions"; context = prompt/instructions + retrieved docs + past state/tool calls/results + memory from related histories + output-format instructions; recommends custom, dense formats (e.g., XML-style event tags) over default chat-message formats for token and attention efficiency; recommends **"hiding errors and failed calls from context window once they are resolved."** [PRACT-OPINION] — [Factor 3 (fetched)](https://github.com/humanlayer/12-factor-agents/blob/main/content/factor-03-own-your-context-window.md). → Render state to subagents as compact, purpose-built views (not raw JSONL dumps); see conflict with Manus on errors (§3).
- **Small, focused agents:** keep agents to "3–10, maybe 20 steps max" because "as context grows, LLMs are more likely to get lost or lose focus"; agents are "one building block in a larger, mostly deterministic system" (a DAG); scope can expand "as LLM context windows become more reliable." [PRACT-OPINION] — [Factor 10 (fetched)](https://github.com/humanlayer/12-factor-agents/blob/main/content/factor-10-small-focused-agents.md). → Size each subagent task to a bounded question; the step ceiling is likely **dated** for 2026 frontier models (Manus reports ~50 tool calls per task, §3), so treat it as a direction, not a number.
- **Unify execution state and business state:** execution state (current step, waiting, retries) "is just metadata about what has happened so far" and can be derived from one event thread; benefits: "one source of truth," "trivially serializable," resume "by just loading the thread," "fork the thread at any point," trivially render to Markdown/UI; caveat: secrets/session IDs stay outside, "minimize those things." [PRACT-OPINION] — [Factor 5 (fetched)](https://github.com/humanlayer/12-factor-agents/blob/main/content/factor-05-unify-execution-state.md). → Strong support for append-only versioned JSONL as the canonical record from which pipeline status is derived, rather than a separate mutable status file.
- **Contact humans with tool calls:** human input/approval is modeled as a structured tool call within the loop, so the agent can pause and resume. [PRACT-OPINION] — [README (fetched)](https://github.com/humanlayer/12-factor-agents). → Represent "ask the founder" / "approve ship" as explicit events in the state log (pause/resume points), not free-text chat.

### Inferences
- 12-Factor and Cognition agree on "own the control flow and the context" but 12-Factor is more permissive of multiple agents *as long as they are small nodes in a deterministic DAG* — i.e., code-orchestrated, not LLM-negotiated. This matches OpenAI's "orchestrate via code" guidance (§4).
- Factor 12 (stateless reducer) + Factor 5 argue that subagents should receive a state snapshot and return an event, never mutate shared state — exactly our centralized-write rule.

### Gaps
- No empirical evidence is offered for any factor; all are practitioner heuristics. No dated changelog of revisions found.

## 3. Manus — "Context Engineering for AI Agents: Lessons from Building Manus" (Yichao "Peak" Ji, July 2025) + Oct 2025 LangChain webinar

### Takeaway
Manus's lessons are production heuristics centered on KV-cache economics and attention management: stable append-only prefixes, masking rather than removing tools, the file system as unbounded restorable memory, a continually rewritten todo.md to "recite" goals, keeping failures visible, and injecting variation to avoid few-shot ruts. In Oct 2025 they framed isolation via sub-agents as one of five context tools, using "share memory by communicating."

### Cited Findings
- **KV-cache hit rate is "the single most important metric for a production agent."** Cached input on Claude Sonnet cost $0.30/MTok vs $3.00/MTok uncached (10x), plus latency gains. [PROD-REPORT] — [Manus blog](https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus) (via search excerpt); [ZenML LLMOps DB](https://www.zenml.io/llmops-database/context-engineering-strategies-for-production-ai-agents). → Keep CLAUDE.md, skill preambles and subagent system prompts byte-stable across runs; put volatile data (dates, run IDs) at the end, not the top.
- **A typical Manus task needs ~50 tool calls; average input:output token ratio ~100:1.** [PROD-REPORT] — [Manus blog](https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus); [search excerpt, agentic-ai KB](https://agentic-ai.readthedocs.io/en/latest/ContextEngineering/manus/). → Agent cost is dominated by re-read input, so every subagent that re-ingests the same corpus multiplies cost; pass distilled findings, not raw pages.
- **Stable prefix + append-only context + deterministic serialization:** even a one-token difference invalidates the cache downstream; do not modify prior actions/observations. [PROD-REPORT/PRACT-OPINION] — [Manus blog](https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus) (via search excerpt). → Emit JSON with sorted keys in scripts that feed the model; never rewrite earlier log lines.
- **"Mask, don't remove":** tool definitions stay static and complete; a state machine masks token logits at decode time to constrain which tools are selectable. Rationale: removing tools mid-run breaks cache and confuses the model about earlier calls. [PROD-REPORT] — [search excerpt](https://agentic-ai.readthedocs.io/en/latest/ContextEngineering/manus/). → In Claude Code, prefer stable tool sets per subagent type and enforce "can't write" via permissions/hooks rather than swapping tool lists mid-session.
- **File system as context:** treat files as unlimited, persistent, agent-operable memory; compression must be *restorable* (e.g., drop a web page's content but keep its URL/path). [PROD-REPORT] — [Manus blog](https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus) [restorable-compression detail not fetched; from primary text]. → Researchers should write full evidence to files and return pointers + short summaries to the main session.
- **Recitation via todo.md:** the agent keeps rewriting a todo list, pushing its objectives into the end of the context to counter "lost-in-the-middle" goal drift over ~50 calls. [PROD-REPORT] — [search excerpt](https://agentic-ai.readthedocs.io/en/latest/ContextEngineering/manus/). → The main session should maintain and re-read a pipeline checklist (e.g., current opportunity, stage, open questions) at each stage transition.
- **"Keep the wrong stuff in":** leave failed actions and stack traces in context so the model updates its beliefs and avoids repeating mistakes. [PROD-REPORT] — [search excerpt](https://agentic-ai.readthedocs.io/en/latest/ContextEngineering/manus/). **Conflicts with** 12-Factor's "hide errors once resolved" ([Factor 3](https://github.com/humanlayer/12-factor-agents/blob/main/content/factor-03-own-your-context-window.md)). → Reconcile: keep failures visible within a run (and log them to JSONL permanently); drop them from *new* subagent briefs once resolved.
- **"Don't few-shot yourself into a rut":** repetitive action/observation pairs make the model imitate the pattern (e.g., reviewing 20 résumés → drift, overgeneralization, hallucination); fix with structured variation in serialization templates, phrasing, ordering. [PROD-REPORT] — [search excerpt](https://medium.com/@balajibal/summary-context-engineering-for-ai-agents-lessons-from-building-manus-a17a7c228425). → Batch-screening many opportunities in one context risks templated verdicts; vary order and consider fresh contexts per item for judgments.
- Manus says it rebuilt its agent framework four times ("Stochastic Graduate Descent"). [PROD-REPORT] — [Manus blog](https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus) [not fetched; from primary text]. → Expect harness churn; keep it simple and versioned.
- **Oct 14, 2025 webinar (with LangChain's Lance Martin):** five context levers — offload (file system/sandbox), reduce (compaction vs summarization), retrieve (file search tools), **isolate (sub-agents)**, cache. For sub-agents: give each the minimum context, communicate via structured contracts/schemas, and "Do not communicate by sharing memory; instead, share memory by communicating." [PRACT-OPINION] — [search excerpts](https://medium.com/@caldasdcardoso/inside-the-langchain-x-manus-webinar-on-context-engineering-69166ee404db); [Lance Martin notes](https://rlancemartin.github.io/2025/10/15/manus/); [video](https://www.youtube.com/watch?v=6_BcCthVvb8). → Supports schema'd subagent outputs merged by one owner; subagents should not read/write a shared scratch state.

### Inferences
- Manus is not anti-multi-agent; it treats sub-agents as a context-isolation tool with typed interfaces, consistent with Cognition 2026 and 12-Factor.
- Parallel subagents each rebuild their own prefix; with a 100:1 input ratio, fan-out multiplies input spend. Isolation must buy enough quality to pay for this.

### Gaps
- Primary post not fetched; the "restorable compression" and "rebuilt four times" details rely on my reading of the original. No post-acquisition (Manus was reported acquired by Meta in late 2025 — unverified here) updates found.

## 4. OpenAI and Google (DeepMind/Research/Cloud) agent-building guidance, 2025–2026

### Takeaway
Both vendors say: maximize a single agent first; split only for tool overload or complex branching; prefer code-driven orchestration for predictability. OpenAI's Feb 2026 "harness engineering" report shifts the emphasis from agent topology to the environment (short map-style AGENTS.md, repo as system of record, mechanical checks). Google's Dec 2025 research gives the strongest quantitative case for *when* multi-agent helps (parallelizable tasks) and hurts (sequential ones).

### Cited Findings
- **OpenAI, "A practical guide to building agents" (2025):** maximize a single agent's capabilities first; split into multiple agents only for complex conditional logic or tool overload. [VENDOR-GUIDE] — [OpenAI guide](https://openai.com/business/guides-and-resources/a-practical-guide-to-building-ai-agents/); [PDF](https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf) (via search excerpt). → Our split must be justified by isolation needs (bias, context size), not by "roles."
- Tool overload is about **overlap, not count**: "some implementations successfully manage more than 15 well-defined, distinct tools while others struggle with fewer than 10 overlapping tools"; first improve tool names/params/descriptions, then split. [VENDOR-GUIDE] — [OpenAI guide](https://openai.com/business/guides-and-resources/a-practical-guide-to-building-ai-agents/) (via search excerpt). → Audit skills for overlapping triggers/descriptions before adding more agents.
- Two patterns: **manager** (central LLM calls specialist agents as tools; edges = tool calls) and **decentralized** (peers hand off execution; edges = handoffs); guardrails are layered and run optimistically alongside the agent. [VENDOR-GUIDE] — [OpenAI guide](https://openai.com/business/guides-and-resources/a-practical-guide-to-building-ai-agents/) (via search excerpt). Human-intervention triggers in the guide: exceeding failure thresholds and high-risk actions [not fetched; from primary text]. → We use the manager pattern; add hooks as guardrails on high-risk actions (publishing, spending, contacting people).
- **OpenAI Agents SDK docs:** "orchestrating via code makes tasks more deterministic and predictable, in terms of speed, cost and performance"; code patterns: structured-output classification for routing, sequential chaining, evaluator loop until criteria met, parallel agents via `asyncio.gather`; for LLM orchestration: good prompts, monitor/iterate, let the agent critique itself, specialized agents, "invest in evals." [VENDOR-GUIDE] — [openai-agents-python docs/multi_agent.md (fetched)](https://github.com/openai/openai-agents-python/blob/main/docs/multi_agent.md). → Fan-out of researchers and the advocate/skeptic/judge sequence should be fixed by scripts/skills, not decided ad hoc by the model.
- **OpenAI, "Harness engineering: leveraging Codex in an agent-first world" (Ryan Lopopolo, Feb 2026):** 5-month internal build of a product with ~1M lines and ~1,500 merged PRs by 3 engineers driving Codex, zero hand-written code; a ~100-line AGENTS.md acts as a *map* pointing to versioned design docs, architecture maps, execution plans and quality grades in the repo; the engineer's job becomes designing environments, specifying intent and building feedback loops. [PROD-REPORT, vendor self-report] — [OpenAI](https://openai.com/index/harness-engineering/) (via search excerpt); [SaaSCity summary](https://saascity.io/blog/harness-engineering-codex-agent-first-openai-2026). → Keep CLAUDE.md short and navigational; put depth in versioned Markdown the agent loads on demand (progressive disclosure via skills).
- **Google, "Introduction to Agents" whitepaper (Nov 2025; Blount, Gulli, Saboo, Zimmermann, Vuskovic)**, part of a 5-part series (architecture, tools, memory, quality, deployment). [VENDOR-GUIDE] — [summary](https://vanducng.dev/2026/01/10/Google-Introduction-to-Agents-Whitepaper-Summary/). Content specifics not retrieved.
- **Google ADK "Developer's guide to multi-agent patterns" (Dec 2025):** 8 patterns from Sequential Pipeline to Human-in-the-loop; the sequential pipeline is praised as "linear, deterministic, and refreshingly easy to debug." [VENDOR-GUIDE] — [Google Developers Blog](https://developers.googleblog.com/developers-guide-to-multi-agent-patterns-in-adk/) (via search excerpt). → Default to deterministic pipelines between stages; reserve LLM routing for genuinely ambiguous branching.
- **Google Research/DeepMind/MIT, "Towards a Science of Scaling Agent Systems" (arXiv 2512.08296, Dec 2025):** (a) *tool–coordination trade-off*: under fixed compute, tool-heavy tasks suffer disproportionately from multi-agent overhead; (b) *capability saturation*: coordination yields diminishing or negative returns once the single-agent baseline exceeds ~45%; (c) *error amplification*: independent agents amplify errors 17.2x vs 4.4x for centralized coordination (orchestrator acts as a "validation bottleneck"); centralized coordination +80.9% on parallelizable financial reasoning; decentralized better on dynamic web navigation (+9.2% vs +0.2%); **all multi-agent variants degraded sequential reasoning/planning by 39–70%**; a predictive model picks the best architecture for 87% of unseen configurations. [EMP-PRE, large controlled study] — [Google Research blog](https://research.google/blog/towards-a-science-of-scaling-agent-systems-when-and-why-agent-systems-work/); [arXiv](https://arxiv.org/abs/2512.08296); [HF papers](https://huggingface.co/papers/2512.08296). → Fan out only decomposable, parallel read tasks; keep sequential reasoning (validation logic, go/no-go) in one agent; always route subagent output through a central validator rather than letting subagents feed each other.

### Inferences
- OpenAI's newest material (harness engineering) says little about topology and much about environment design; the frontier practice has moved from "how many agents" to "what does each agent see and how is it checked."
- The ~45% saturation finding implies that as models get stronger at a task, the marginal value of adding agents to that task falls; our harness should periodically re-test whether a subagent split still beats a single well-briefed session.

### Gaps
- Could not verify whether OpenAI or Google DeepMind published a newer (2026) general agent-building guide beyond the harness-engineering post; searches surfaced none.
- Exact configuration counts, benchmarks list and model families of the scaling study were not retrievable from excerpts (benchmarks reportedly include Finance-Agent, BrowseComp-Plus, PlanCraft, Workbench — unverified).

## 5. Empirical results: failure taxonomies, single vs multi-agent, debate vs self-consistency, production reliability

### Takeaway
The empirical record is consistent: multi-agent failures stem mostly from specification and coordination rather than model capability; multi-agent debate rarely beats simple majority voting/self-consistency at equal compute; MAS advantages shrink as frontier models improve and invert on sequential tasks; production agents that work are short, structured, and human-supervised. The one strong pro-adversarial result is for *judging*: debate between opposing advocates improves a weaker judge's accuracy versus a single persuader.

### Cited Findings
**Failure taxonomy**
- **MAST (Cemri, Pan, Yang et al., UC Berkeley; arXiv 2503.13657; NeurIPS 2025):** 14 failure modes in 3 categories — specification/system design (41.77%), inter-agent misalignment (36.94%), task verification (21.30%); original version built from 150 traces with expert inter-annotator agreement κ = 0.88; later version released MAST-Data with 1,600+ annotated traces across 7 MAS frameworks and an LLM-as-judge annotator reported at 94% accuracy / κ 0.77. [EMP-PR] — [arXiv](https://arxiv.org/abs/2503.13657); [NeurIPS poster](https://neurips.cc/virtual/2025/poster/121528); [MAST site](https://sites.google.com/berkeley.edu/mast/home); percentages via [search excerpt](https://arxiv.org/html/2503.13657v3); judge-accuracy figure only from aggregator [orq.ai](https://orq.ai/blog/why-do-multi-agent-llm-systems-fail). Note: v1 (Mar 2025) numbers (150 traces, fewer frameworks) are **superseded** by the v3 dataset. → ~79% of failures are spec + coordination: invest in precise subagent briefs, explicit termination criteria and a verification step, not more agents.
- Worst offenders named in summaries: task misinterpretation, context loss, incorrect verification, premature termination. [Secondary] — [Future AGI summary](https://futureagi.substack.com/p/why-do-multi-agent-llm-systems-fail). → Subagent briefs need "done" criteria and a required-fields output schema checked by a script.
- Comparing MetaGPT and ChatDev on the same model (GPT-4o): MetaGPT's SOPs reduced system-design and inter-agent-misalignment failures by 60–68%, while ChatDev's explicit test/review phases better mitigated verification failures. [EMP-PR, via search excerpt; attribution to MAST v3 likely but unverified] — [MAST search excerpt](https://sites.google.com/berkeley.edu/mast/home). → Written SOPs (skills) and explicit review phases address different failure classes; we need both.

**Single vs multi-agent**
- **"Single-agent or Multi-agent Systems? Why Not Both?" (arXiv 2505.18286, 2025):** benefits of MAS over SAS diminish as LLM capability improves (o3, Gemini 2.5 Pro reduce the limitations that motivated MAS); a hybrid "request cascading" gives +1.1–12% accuracy and up to 20% lower cost. [EMP-PRE] — [arXiv](https://arxiv.org/abs/2505.18286). → Default single-session; escalate to fan-out only when a cheap single pass is insufficient.
- **"Towards a Science of Scaling Agent Systems"** (see §4): +80.9% on parallelizable tasks, −39% to −70% on sequential ones; 17.2x vs 4.4x error amplification. [EMP-PRE] — [arXiv](https://arxiv.org/abs/2512.08296). → Task shape, not "more agents," determines the sign of the effect.
- **LangChain "Benchmarking Multi-Agent Architectures" (June 2025, τ-bench variant with extra distractor domains):** single agent degraded significantly as distractor domains/context were added; swarm slightly beat supervisor; supervisor improved ~50% after removing handoff messages from sub-agent context and forwarding sub-agent messages directly. [EMP, vendor benchmark, not peer-reviewed] — [LangChain blog](https://www.langchain.com/blog/benchmarking-multi-agent-architectures) (via search excerpt). → Counterpoint in favor of splitting: when one agent must carry many unrelated tool domains, isolation helps; and passing subagent output verbatim beats letting the manager paraphrase it.
- **"Decomposition Buys Integrity, Not Yield" (Rong He, arXiv 2609.17464, 15 Sep 2026):** models decomposition trees; under measured retention r(b)=Cb^−δ, flat is optimal for *yield* (how many leaf findings reach the root) and no arrangement escapes the exponent; on 600 production deep-research traces δ = 0.34 [0.30, 0.38]; decomposition improves *integrity*; balancing yield, integrity and cost gives an optimum of two or three tiers. [EMP-PRE, single-author, 9 days old, unreviewed] — [arXiv](https://arxiv.org/abs/2609.17464). → Keep research fan-out shallow (main session → researchers, maybe one more tier); expect findings to be lost at each summarization hop, so have researchers write full findings to files.
- **"Language Model Teams as Distributed Systems" (Mieczkowski, Collins, Sucholutsky, Vélez, Griffiths; arXiv 2603.12229, Mar 2026):** argues distributed-computing principles explain LLM-team inefficiencies (when a team helps, how many agents, structure effects). [EMP-PRE / conceptual] — [arXiv](https://arxiv.org/pdf/2603.12229). → Treat subagents like distributed workers: minimize coordination, avoid shared mutable state, single writer.

**Debate vs self-consistency / voting**
- **"Rethinking the Bounds of LLM Reasoning: Are Multi-Agent Discussions the Key?" (Wang et al., ACL 2024):** a single agent with a strong prompt nearly matches the best multi-agent discussion across reasoning tasks and backbones; discussion helps only when the prompt has no demonstrations. [EMP-PR] — [ACL Anthology](https://aclanthology.org/2024.acl-long.331/). → Invest in the judge's rubric/examples before adding discussants.
- **"Should we be going MAD?" (Smit et al., ICML 2024):** multi-agent debate does not reliably beat self-consistency or multi-path ensembling; some MAD variants (e.g., Multi-Persona) win after tuning but are hyperparameter-sensitive and hard to optimize. [EMP-PR] — [PMLR](https://proceedings.mlr.press/v235/smit24a.html). → Debate-style exchanges are fragile; prefer independent samples + aggregation.
- **"Debate or Vote" (arXiv 2508.17536, 2025):** across 7 NLP benchmarks, majority voting of initial answers accounts for most of MAD's gains and matches or beats MAD configs; theory: debate induces a martingale over beliefs, so debate alone doesn't raise expected correctness. [EMP-PRE + theory] — [arXiv](https://arxiv.org/abs/2508.17536). → Our advocate/skeptic setup should not be a multi-round debate; independent isolated passes + one judge is closer to the evidence-backed configuration.

**Adversarial arguments for a judge (supports advocate/skeptic + judge)**
- **Khan et al., "Debating with More Persuasive LLMs Leads to More Truthful Answers" (ICML 2024):** with debate, non-expert LLM judges reach 76% and human judges 88% accuracy vs naive baselines of 48% and 60%; more persuasive debaters raise judge accuracy, whereas more persuasive single consultants *lower* it. [EMP-PR] — [arXiv](https://arxiv.org/abs/2402.06782). → Two opposing advocates beat one persuader in front of a judge; a lone "advocate" report without a skeptic is dangerous.
- **Kenton et al. (Google DeepMind), "On scalable oversight with weak LLMs judging strong LLMs" (NeurIPS 2024):** debate consistently outperforms consultancy across extractive QA, math, coding, logic and multimodal tasks; stronger debaters increase judge accuracy more modestly than prior work; with self-chosen positions, judges are less often convinced of wrong answers under debate than consultancy. [EMP-PR] — [arXiv](https://arxiv.org/abs/2407.04622); [NeurIPS](https://proceedings.neurips.cc/paper_files/paper/2024/hash/899511e37a8e01e1bd6f6f1d377cc250-Abstract-Conference.html). → Supports opposing cases, but gains over the judge simply answering directly are not guaranteed (see Gaps).
- **LLM-judge bias:** judges (e.g., GPT-4o, Claude 3.5 Sonnet) systematically score their own outputs higher and show *family bias* toward same-family models; self-preference is linked to lower perplexity (familiarity) of the text; position bias is documented across families. [EMP-PRE] — [Wataoka et al., arXiv 2410.21819](https://arxiv.org/abs/2410.21819); [Play Favorites, arXiv 2508.06709](https://arxiv.org/pdf/2508.06709) (attribution of the 5,000-pair / 9-judge study between these two is uncertain from excerpts); new: [Who Judges Matters, arXiv 2609.17857](https://arxiv.org/pdf/2609.17857). → A Claude judge in the main session evaluating Claude-written advocate/skeptic briefs shares family bias; randomize/blind order and labels, and where stakes are high consider a cross-family or human check.

**Production reliability**
- **"Measuring Agents in Production" (arXiv 2512.04123; ICLR 2026):** 20 in-depth case studies + survey of practitioners with deployed systems across 26 domains: 68% of production agents execute ≤10 steps before human intervention (47% ≤5), 70% prompt off-the-shelf models without weight tuning, 74% rely primarily on human evaluation; most use developer-defined structured workflows with autonomy confined to specific nodes; reliability is the top challenge, handled by systems-level design. [SURVEY/EMP-PR] — [arXiv](https://arxiv.org/abs/2512.04123); [OpenReview](https://openreview.net/forum?id=AsvLggSOvS). → Our script-orchestrated pipeline with human gates is the modal successful production shape.
- **LangChain "State of Agent Engineering" (survey Nov 18–Dec 2, 2025; 1,340 responses):** 57% have agents in production; quality is the top barrier (32%), latency second (20%); cost concerns fell vs 2024. [SURVEY, vendor-run, self-selected] — [LangChain](https://www.langchain.com/state-of-agent-engineering); [KDnuggets overview](https://www.kdnuggets.com/the-state-of-agent-engineering-report-overview). → Optimize for verdict quality and auditability over token cost.
- **Chroma "Context Rot" (July 2025):** all 18 tested models (incl. GPT-4.1, Claude 4, Gemini 2.5, Qwen3) degrade as input length grows, non-uniformly; distractors and needle–question similarity matter; counterintuitively, logically coherent haystacks hurt more than shuffled ones. [EMP, vendor research, not peer-reviewed] — [Chroma](https://www.trychroma.com/research/context-rot) (via search excerpts; aggregator claims of "30–50% drops" not verified). → The main reason to isolate is context hygiene: keep raw search noise out of the judge's context.

### Inferences
- Across studies, the reliable gains attributed to "multi-agent" come from (a) independent sampling + aggregation, (b) context isolation for breadth, and (c) adversarial presentation to a judge — not from agents conversing.
- Error amplification (17.2x independent vs 4.4x centralized) and MAST's verification category both argue for a mandatory central verification step between subagent output and any state write.

### Gaps
- Could not verify MAST v1's reported intervention result (I recall "+14% for ChatDev from improved role specs/topology, insufficient overall" from the v1 abstract — unverified here).
- Could not verify Kenton et al.'s debate-vs-direct-QA comparison (recollection: debate beat direct QA only with information asymmetry; mixed otherwise).
- No non-Anthropic study found that directly measures token cost multipliers of multi-agent vs single-agent in production; the "Why not both" paper gives only relative cost reductions from cascading.
- No study found on advocate/skeptic *isolation* specifically for business-opportunity validation; evidence is transferred from QA/reasoning tasks.

## 6. Synthesis: when do multi-agent designs help vs hurt?

### Takeaway
Multi-agent helps when subtasks are decomposable, mostly read-only, and their results can be merged by one owner (breadth-first research, independent samples, clean-context review, adversarial briefs for a judge). It hurts when subtasks share implicit decisions, when work is sequential, when agents write to shared artifacts, when agents negotiate peer-to-peer, or when the single-agent baseline is already strong. The current harness design is on the "helps" side of every line, with specific risks to manage (summarization loss, family-biased judging, fan-out cost, brief quality).

### Cited Findings
- Read-heavy multi-agent systems are "far more tractable" than write-heavy ones because reads parallelize and writes don't; even read-heavy systems need careful context engineering (vague subagent briefs cause duplicated/misread work). [PRACT-OPINION] — [LangChain, "How and when to build multi-agent systems" (Harrison Chase, June 2025)](https://www.langchain.com/blog/how-and-when-to-build-multi-agent-systems) (via search excerpt). → Our read-only researcher fan-out is the favored case; brief quality is the main lever.
- Writes single-threaded; extra agents contribute intelligence, not actions. [PRACT-OPINION] — [Cognition 2026](https://cognition.com/blog/multi-agents-working). → Keep all state writes in the main session/scripts.
- Parallelizable tasks: +80.9% with centralized coordination; sequential tasks: −39% to −70% for every multi-agent variant; saturation above ~45% single-agent baseline; independent agents amplify errors 17.2x vs 4.4x centralized. [EMP-PRE] — [arXiv 2512.08296](https://arxiv.org/abs/2512.08296). → Fan out breadth, never depth; keep a central validator.
- Voting ≈ debate; single well-prompted agent ≈ discussion. [EMP-PR/PRE] — [Debate or Vote](https://arxiv.org/abs/2508.17536); [Smit et al.](https://proceedings.mlr.press/v235/smit24a.html); [Wang et al.](https://aclanthology.org/2024.acl-long.331/). → Don't add debate rounds; spend budget on independent samples and rubric quality.
- Debate > consultancy for judge accuracy. [EMP-PR] — [Khan et al.](https://arxiv.org/abs/2402.06782); [Kenton et al.](https://arxiv.org/abs/2407.04622). → Keep both advocate and skeptic; never ship a verdict from a single-sided case.
- Flat/shallow trees maximize yield; 2–3 tiers optimal when integrity and cost are included. [EMP-PRE] — [arXiv 2609.17464](https://arxiv.org/abs/2609.17464). → Max depth 2 (main → researchers); no sub-sub-agents.
- Many unrelated tool domains in one agent degrade it; isolation helps there. [EMP, vendor benchmark] — [LangChain benchmark](https://www.langchain.com/blog/benchmarking-multi-agent-architectures). → A legitimate reason to split is tool/domain overload, e.g., a "shipping" agent vs a "research" agent with different toolsets.

Condition table (derived from the findings above):

| Condition | Multi-agent tends to | Evidence |
|---|---|---|
| Breadth-first, read-only search over independent sources | Help | Kim et al. +80.9% parallelizable; LangChain read vs write; Cognition read-only subagents |
| Independent samples + aggregation (voting) | Help (cheaply) | Debate or Vote; Smit et al. |
| Clean-context review of an artifact | Help | Cognition Code-Review Loop; MAST verification category |
| Opposing advocates before a judge | Help judge accuracy | Khan et al.; Kenton et al. |
| Many unrelated tool domains in one prompt | Help (isolation) | LangChain τ-bench variant; OpenAI tool-overlap guidance |
| Sequential reasoning / planning where each step depends on the last | Hurt (−39% to −70%) | Kim et al. |
| Parallel writers to one artifact / shared decisions | Hurt (incoherence) | Cognition Principles 1–2, Flappy Bird |
| Peer-to-peer negotiation / swarms / multi-round debate | Hurt or no gain | Cognition 2026; Debate or Vote; MAST misalignment 36.94% |
| Strong single-agent baseline (>~45%) | Diminishing/negative | Kim et al.; "Why not both" |
| Deep hierarchies (>2–3 tiers) | Lose findings | Decomposition Buys Integrity, Not Yield |
| Tool-heavy tasks under fixed budget | Hurt | Kim et al. tool–coordination trade-off |

### Inferences
- **Our design is consistent with the evidence**, with these risks to manage:
  1. *Brief under-specification* (MAST's largest category): researcher briefs should carry thesis context, exclusions, done-criteria and an output schema; validate returns with a script before merging.
  2. *Summarization loss* (Decomposition paper; LangChain supervisor fix): researchers should write full evidence to files and return pointers + structured findings; the judge reads evidence directly where it matters.
  3. *Judge bias* (self/family/position bias): blind the judge to which brief is advocate vs skeptic, randomize order, and give it an explicit rubric with examples (Wang et al. shows prompts/demos close most of the gap).
  4. *Debate creep*: keep advocate and skeptic as independent single-pass briefs; do not let them respond to each other in rounds (Debate or Vote; Smit et al.).
  5. *Cost*: with ~100:1 input ratio (Manus), each fan-out re-reads context; keep subagent system prompts/skill preambles stable for caching and pass distilled context.
  6. *Sequential validation steps* (e.g., unit economics → pricing → go/no-go) should stay in one thread, per the −39–70% sequential result.
  7. *Re-test the split periodically*: capability saturation means a single well-briefed session may overtake the multi-agent setup on some stages as models improve.
- The main *counterargument that still applies* to us is not "multi-agent fails" but "the value comes from isolation and independence, not from agent count or conversation"; any added agent should be justified by one of: context isolation, independence of samples, clean-context review, or adversarial presentation.

### Gaps
- No direct empirical comparison found of "advocate + skeptic + blind judge" vs "single agent self-critique" on open-ended business/strategy judgments; the transfer from QA benchmarks is an assumption.
- No non-Anthropic production data on Claude Code subagents specifically.
- The newest items (Decomposition paper, Sept 2026; Who Judges Matters, Sept 2026; "Harness Engineering: Anatomy... of Coding Agents," [arXiv 2609.00006](https://arxiv.org/pdf/2609.00006)) were found but not read beyond abstracts/titles.
